# 游戏任务系统最终方案

> 状态：任务引擎已按本方案落地。验收脚本是 `scripts/check-task-engine.ts`。粮食、行军、拜访和百支军队规模的世界模拟还不在这套引擎里。  
> 上位约束：在线 Tick 与离线 `advance` 必须经过同一个绝对时间边界推进器；不得先把时钟跳到目标再回头补 Task。  
> 配套文档：[任务队列数据结构评审](任务队列数据结构评审.md)、`docs/世界架构/` 各文件（已同步本口径）。

## 1. 最终结论

世界由**受控时间推进器**推动，Task 由绝对 `nextSettleAt` 触发：

1. `WorldClock.TotalGameTime` 是唯一权威游戏时间；内部使用整数 fixed-point（或整数秒 + 持久化余数），避免分段推进产生浮点漂移。
2. `RunningTicker` 只提交真实时间增量，`WorldDriver` 将其换算成目标游戏时间，并逐个推进到 `nextSettleAt`、PauseWorld 或目标边界。
3. `TaskSettleLevel` 只负责从 `StartTime` 计算下一个 cadence；Minute/Hour/Day/Month/Year 监听器不再分别直接执行 Task。
4. `_tasks` / `_todayTasks` 是可重建的两级 ScheduleIndex：未来按绝对日、今日按日内分钟索引 `nextSettleAt`，不是时间源和权威 Task 数据。
5. `TaskSequenceType` 只表示分类、阶段和默认排序，**不表示互斥锁**。互斥和等待由显式 `resourceClaims`、`dependsOn`、`serialKey` 决定。
6. Async Task 进入 PendingExecution 后让出调度器；只有冲突资源的 Task 等待。只有 `TimePolicy=PauseWorld` 才停止世界时间。
7. 权威状态提交严格串行，但 CommitGate 必须校验实体版本/read-set；“串行”本身不能防止旧 ChangeSet 覆盖新状态。

核心不变量：

- 时钟不能越过尚未处理的 PauseWorld 或 Task 边界。
- 长周期行为保存为 Activity / Active Task，只安排下一结算点，不用一个回调占住执行器。
- 到期、取得执行权、提交三个阶段都要复验；Async 结果不能持有调度器或提交器。
- `dueAt`、`startBefore`、`commitBefore`、`activeUntil` 分开表达，禁止继续复用一个 EndTime 承担全部语义。
- 过期、末段、重入、恢复和外部输入策略均由 Task 类型显式声明。



## 2. 双时间轴


| 轴      | 模块                         | 单位       | 用途                                     |
| ------ | -------------------------- | -------- | -------------------------------------- |
| 真实时间   | `RealTimeCounter`          | 秒（可扩展毫秒） | 游玩时长、UI、真实超时                           |
| 游戏世界时间 | `WorldClock.TotalGameTime` | 整数累计游戏时间 | `dueAt` / `nextSettleAt` / deadline、活动生命周期、存档 |


显示层用 `date-utils` 把累计游戏时间格式化为游戏历（月 30 日、年 12 月）。Task 最低结算粒度为游戏分钟；写入调度器前必须量化到合法边界，不能用 `floor` 让任意秒级时间提前触发。

## 3. 总体架构

```text
RunningTicker(realDelta) / 离线目标时间
    |
    v
WorldDriver（唯一推进协调器）
    ├─ targetGameTime
    ├─ ScheduleIndex.peekNextSettleAt()
    └─ PauseWorld 边界
    |
    | 每次只把 WorldClock 原子推进到最近边界
    v
TaskManager
    +-> TaskRepository（权威 TaskRecord）
    +-> FutureDayTable / TodayMinuteTable（可重建索引）
    +-> drainDueAt(boundary) -> TaskExecutionRequest
    |
    v
TaskPipeline
    TriggerGate
      -> ReadyScheduler（deadline / priority / sequence）
      -> DependencyGraph / ResourceArbiter
      -> StartGate
      -> Executor / PendingExecution
      -> CommitGate（readSet / entityVersion / idempotency）
      -> SerialCommitQueue
      -> Finalizer
    |
    v
WorldMutation（原子提交）+ 日志 / 去重表 / 后续 Task
```

`assets/src/task` 目标模块划分（实现阶段）：


| 模块 | 职责 |
| --- | --- |
| `task-define.ts` | cadence、deadline、资源/依赖、TimePolicy、过期/重入/恢复策略 |
| `task-base.ts` | TaskRecord 权威字段和生命周期；单次执行拆到 ExecutionRecord |
| `task-manager.ts` | TaskRepository、两级 ScheduleIndex、到期请求生成 |
| `task-sequence.ts` | ReadyScheduler；按 deadline、priority、sequence 选择可运行请求 |
| `task.ts` | 具体 Task 子类或工厂 |


世界侧：`world-clock.ts` 只保存并原子设置时间；`world-driver.ts` 负责在线/离线统一边界推进。`listen_min/hour/day/month/year` 可保留为 UI/派生系统通知，但不得成为权威 Task 调度顺序。

## 4. TaskSettleLevel：cadence 元数据

`TaskSettleLevel` 只用于从固定 `StartTime` 计算 `nextSettleAt`，不是监听器、队列、执行器或互斥范围。

| 级别 | 周期 | 相对边界示例 |
| --- | --- | --- |
| Minute | 1 游戏分钟 | Start + k 分钟 |
| Hour | 1 游戏小时 | Start + k 小时 |
| Day | 1 游戏日 | Start + k 游戏日 |
| MultiDay | N 游戏日 | Start + k×N 日 |
| Month | 30 游戏日 | Start + k×30 游戏日 |
| Year | 360 游戏日 | Start + k×360 游戏日 |

每次 Finalizer：

1. 根据原始 StartTime、cadence 和已完成序号计算下一个绝对时刻。
2. 强制 `nextSettleAt > currentSettleAt`，防止同时刻无限重排。
3. 把同一个 TaskRecord 的下一次执行引用写入 ScheduleIndex。

资源结算、战斗阶段结算、剧情结算都使用**同一条 TaskPipeline**。所谓“结算 Task”只是 `TaskSequenceType`、handler 和 payload 不同，不建立单独的 Settlement Executor。

**末段不足一个周期**（在 `activeUntil` 前凑不满整周期）由任务类型的 `PartialSettlementPolicy` 声明。

### 4.1 `listen_*` 的能力边界

当前 `WorldClock` 的分级通知发生在 `TotalGameTime` 已经加到目标之后，而且顺序是内层到外层：

```text
min -> hour -> day -> month -> year
```

它不能保证：

- 跨级 Task 的绝对时间顺序；
- 从 09:09 跳到 09:16 时精确停在 09:10 PauseWorld；
- 新日分钟 Task 在 `listen_day` 晋升前不被遗漏；
- 监听器抛错时钟仍保持原子状态。

因此 `listen_*` 只能作为派生通知。权威 Task 流程由 WorldDriver 按统一绝对边界驱动；WorldClock 应先原子完成钟面状态，再发布不可变的 `TimeAdvanced(from, to)` 通知，并隔离订阅者异常。

### 4.2 两级直址表是 ScheduleIndex 优化

两张表采用**粗粒度日表 + 细粒度分钟表**：

- `_tasks`：未来表，以滚动 epoch 下的游戏日为 unit，保存非今日 `nextSettleAt`。
- `_todayTasks`：今日表，以日内分钟 `0..1439` 为 unit。
- `addTask`：今日任务直接进今日表；未来任务按日进入总表。
- WorldDriver 到达日边界时：晋升新日槽，再继续处理下一绝对边界。

槽定位接近 `O(1)`，但槽内有序数组插入仍是 `O(m)`；不能把整体插入复杂度写成 O(1)。固定窗口之外必须有 overflow 索引或滚动迁移，不能在五年后越界。

位图查找最坏为 `O(W/32)=O(W)`，只是常数缩小。今日 1440 槽最多扫描 45 个 word，五年 1800 日约 57 个 word，实际可控；但不能每次都从槽 0 重扫。ScheduleIndex 应缓存 `minOccupiedSlot / scanCursor`，使时间单调前进时整窗摊还只扫描一次；窗口扩大时再增加摘要位图（近似 `O(log₃₂W)`）或 occupied-slot heap。

同一分钟槽内全部按绝对 `nextSettleAt`、阶段、priority、sequence 排序并一次 drain；不再按 settleLevel 等待不同监听器。ScheduleIndex 需要 `peekNextDueAt()`、`drainAt(dueAt)`、滚动窗口和 overflow API。

长周期 Task 只把**下一结算点**放入两级表。结算后，管线按相对 `StartTime` 算出下一个 `nextSettleAt` 并重新调度。Task 的生命周期仍可保持 Active，调度项不会占住执行器。

### 4.3 分类、互斥、依赖和时停必须分开

| 维度 | 回答的问题 | 当前工程对应字段/结构 |
| --- | --- | --- |
| `TaskSequenceType` | 属于什么阶段、默认如何排序？ | ResourceSettlement / BattleSettlement / Story / Task / System / Other |
| `resourceClaims` / `serialKey` | 和谁互斥？ | 领域资源键及读写模式 |
| `dependsOn` | 必须等谁完成？ | execution/task 依赖图 |
| `ExecutionMode` | 同步返回还是异步回流？ | Sync / Async |
| `TimePolicy` | 是否暂停世界时间？ | ContinueWorld / PauseWorld |

`TaskSequenceType` 不能继续作为互斥 Lane。相同类型但资源不冲突的 A/B 可以并发准备；不同类型但写同一实体的任务必须互斥或在 CommitGate 发生版本冲突。Async Waiting 让出调度器，但可按业务规则继续持有显式领域资源；不得持有全局提交器。

## 5. 长周期 Task 与 A/B 吞噬问题

**反例**：按 TaskSequenceType 建一条 concurrency=1 的串行 Lane。A 等待异步结果时占住整类 Task，B 虽在有效窗口到期，也只能等到过期。

**本方案**：

- 长周期 A 保持 Activity/Active 状态，只在边界生成短 execution，不长期占用 ReadyScheduler。
- A、B 可以拥有相同 TaskSequenceType；只有 `resourceClaims` 或 `dependsOn` 冲突时才等待。
- A 可占用 `story:main`，C/D 声明依赖该资源，因此等待；B 使用 `settlement:clock`，在 09:12 正常启动。
- ReadyScheduler 遇到资源阻塞的 C/D 时要移入 `resourceWaiters` 并继续寻找可运行的 B，禁止队头阻塞。
- 若 A 的某次结算声明 `PauseWorld`：仅 **advance** 路径在该时刻停住；在线 Tick 是否暂停由产品规则与 `EnableTick` 统一控制（默认：PauseWorld 时不再累加 `TotalGameTime`，直到解除）。



## 6. 【阻塞】语义（必读）

“执行尚未完成”“资源互斥”“业务依赖”“暂停世界”是四个维度。禁止用一个 Block 布尔同时表达。

### 6.1 ExecutionMode（怎么得到执行结果）

| 值 | 含义 |
| --- | --- |
| `Sync` | handler 同步返回结果 |
| `Async` | Promise、用户输入、HTTP 等稍后返回；登记 PendingExecution 后让出调度器 |

### 6.2 ResourcePolicy（资源互斥）

TaskExecutionRequest 显式声明 `resourceClaims`，至少区分 Read / Write / Exclusive。相同 TaskSequenceType 不自动互斥；冲突资源进入对应 waiters。多资源获取必须统一排序或一次性 try-acquire，避免死锁。

### 6.3 DependencyPolicy（业务依赖）

`dependsOn` 表达“C 必须等 A 成功/结束”，并在入队时检查依赖环。依赖等待不能占用执行器；依赖失败时按 Skip / Cancel / Compensate 等策略处理。

### 6.4 TimePolicy（世界时间维度）


| 值               | 含义                                                   |
| --------------- | ---------------------------------------------------- |
| `ContinueWorld` | 默认；该 Task 等待时不停止世界时钟                                 |
| `PauseWorld`    | 显式时停；`advance` 在此刻停止并返回；在线时通常配合 `EnableTick = false` |


示例：

- A 为 `Async + ContinueWorld` 并占用 `story:main`；C/D 需要同一资源，因此等待。
- B 与 A 同为 Task 类型，但只需要 `settlement:clock`，所以 09:12 正常启动。
- 必须等玩家二选一且世界不能继续：`Async + PauseWorld`。

还必须禁止 handler 用同步死循环或长时间 CPU 计算阻塞 JavaScript 线程；那会让 `RunningTicker` 本身无法 Tick。重计算应拆帧、分段或放进 Worker。

## 7. Task 管线：调度与有效性必须分开

当前工程同时缺少“受控绝对边界推进”和 `TaskManager` 之后的完整执行管线。目标阶段固定为：

```text
WorldDriver 到达绝对时间边界
  -> TaskManager / ScheduleIndex：drainAt(nextSettleAt)
  -> TriggerGate：检查这次时间触发是否仍有效
  -> TaskExecutionRequest
  -> ReadyScheduler：按 deadline、priority、sequence 排序
  -> DependencyGraph / ResourceArbiter：选择第一个可运行请求
  -> StartGate：真正开始前复验（尤其检查 startBefore）
  -> OverlapGate：处理同 Task 上一次 execution 尚未完成的情况
  -> Executor：执行同步 handler，或启动异步工作
  -> CommitGate：异步回流/同步提交前再次复验
  -> SerialCommitQueue：串行提交权威状态
  -> Finalizer：更新状态、重排或进入终态
```

结算 Task 与剧情、战斗等普通 Task 从 `TaskExecutionRequest` 开始完全共用这条管线。差别仅在 handler、payload、`TaskSequenceType` 和策略配置。

### 7.1 ScheduleIndex 与 ReadyScheduler 不要混名

**ScheduleIndex（TaskManager 两级表）**只回答“什么时候到期”：

- 根据 `nextSettleAt` 放入 `_tasks` 或 `_todayTasks`。
- 日切时把总表对应日槽晋升到今日表。
- WorldDriver 到达绝对 boundary 时调用 `drainAt(boundary)`。
- 生成 `TaskExecutionRequest`，不直接运行 handler。

**ReadyScheduler**只回答“已经到期的请求谁先尝试运行”：

- 默认按 `startBefore`（最早 deadline）、priority、sequence 排序。
- TaskSequenceType 可参与阶段排序，但不作为互斥键。
- 资源冲突请求移到 `resourceWaiters[resourceKey]`，调度器继续扫描后续可运行请求，避免队头阻塞。
- 依赖未满足请求进入 dependency waiters；依赖完成后重新入 Ready。
- 如需 QoS Lane，只用于预算和配额，不承担业务互斥正确性。

时间表命中或已经进入 ReadyQueue，都**不代表 Task 获得不可撤销的执行权**。

### 7.2 ValidityGate 在三个安全点运行

同一套规则至少在三个安全点运行：

1. **TriggerGate**：从今日表取出时，过滤已取消、重复触发等明显无效项。
2. **StartGate**：真正取得执行权时检查 `startBefore`、依赖和资源声明，并原子获取资源。
3. **CommitGate**：异步结果回流或 ChangeSet 提交前，检查 `commitBefore`、revision、readSet/entityVersion、幂等键及关键前置条件。

校验内容：

1. 生命周期状态是否允许执行（非 Dead / Canceled / Completed）。
2. 当前时刻是否超过 startBefore / commitBefore；分别应用对应 LatePolicy。
3. `taskRevision` / `activityRevision` 是否仍匹配。
4. `RepeatCount`、当前结算序号与 `nextSettleAt` 是否匹配，防止重复触发。
5. 业务依赖、资源 claim、实体 readSet/version 是否仍成立。
6. `executionId` / 幂等键 / commitSequence 是否已经提交。

校验输出应是结构化决定：`Execute`、`Skip`、`Expire`、`Reschedule`，并记录 reason。Scheduler 不修改这些决定。

### 7.3 Executor 与提交

```text
1. StartGate -> Execute
2. Sync -> 计算 ChangeSet -> CommitGate -> SerialCommitQueue -> 原子提交
3. Async -> 启动外部工作并持久化 PendingExecution（executionId, revision, resources, recoveryPolicy, 幂等键）
      -> execution 进入 Waiting
      -> 立即让出 ReadyScheduler；仅按 ResourcePolicy 保留显式领域资源
      -> Promise / 用户输入 / HTTP 完成
      -> ResultCommand 回流
      -> CommitGate 再验
      -> SerialCommitQueue 串行提交
4. Finalizer -> 释放资源；唤醒资源/依赖 waiters；重排下一结算点或进入终态
```

Promise 可以作为**一次外部异步工作的句柄**，但不能用一条全局 Promise chain 串行所有 Task，也不能持久化 Promise。权威状态在任何 `await` 前不保持“提交了一半”的中间态。

`TaskManager` 只做同步 `submit(request)` 入队，**绝不能 await A 的 Promise**。A Waiting 时 ReadyScheduler 继续寻找不冲突的 B。

**SerialCommitQueue**：任意时刻只有一个 ChangeSet 在提交；提交临界区内禁止 await。ChangeSet 必须携带 readSet/entityVersion，CommitGate 在当前世界状态下重新验证后才可原子应用。

**重入**：同一 Active Task 上一次 execution 仍在 Waiting，下一个结算边界又到了 —— 由 `OverlapPolicy` 声明：


| 策略       | 行为                         |
| -------- | -------------------------- |
| Coalesce | 合并为一次待结算区间                 |
| Queue    | 排队，逐次 execution            |
| Skip     | 跳过本次边界                     |
| Parallel | 允许多个 execution 并行等待（提交仍串行） |




所有 Async execution 必须配置超时、取消和恢复策略；成功、失败、取消、超时、CommitGate 拒绝都通过 `finally` 释放资源。依赖图必须拒绝环，资源获取必须避免多锁死锁。

### 7.4 ResultCommand 回流协议

Promise 完成不能直接修改 WorldState，也不能重入 WorldDriver。它只生成不可变 ResultCommand，投递到 ResultInbox：

```text
ResultCommand
  commandId
  executionId / taskId / taskRevision
  externalCorrelationId?
  acceptedAtGameTime          // 内核安全点接收时的当前游戏时间
  completedAtRealTime         // 仅诊断
  success / payload / errorCode
  idempotencyKey
```

消费流程：

```text
Promise.then / catch
  -> durable ResultInbox.enqueue
  -> 等当前 advanceSlice / boundary batch 返回
  -> 按 commandSequence 在安全点 drain
  -> 查 ExecutionRecord / correlationId / 幂等账本
  -> CommitGate(deadline, revision, readSet/version)
  -> 生成 ChangeSet
  -> SerialCommitQueue
  -> 同一事务更新 WorldState、ExecutionRecord、幂等账本
  -> Finalizer 释放资源并唤醒依赖
```

安全点可位于每帧推进前或一个绝对 boundary 完成后。重复、迟到、已取消、revision 不符的结果只记录原因，不产生副作用。崩溃恢复使用 Retry / Reissue / QueryRemote / Cancel / Compensate；Promise 本身不持久化。

### 7.5 A / B / C / D 完整运行例子

前提：

- A、B、C、D 可以具有相同 `TaskSequenceType`。
- A：09:10 到期，`Async + ContinueWorld`，独占资源 `story:main`。
- B：09:12 到期，`startBefore=09:15`，只使用 `settlement:clock`。
- C、D：需要 `story:main`，因此等待 A；不是因为类型或队列相同。
- 现实时间 : 游戏时间 = `1 : 100`。游戏走 10 分钟（600 秒）只需现实 6 秒。

当天开始时，A/B 等定时 Task 已由未来表晋升到今日表：A 位于日内分钟 550，B 位于 552。

```text
现实 +0s / 游戏 09:10
  WorldDriver 到达 A.nextSettleAt
  -> A 从 _todayTasks 取出
  -> TriggerGate 通过
  -> ResourceArbiter 获取 story:main
  -> A 开始异步执行并登记 PendingExecution
  -> A Waiting 并让出 ReadyScheduler
  -> C/D 因 story:main 冲突进入 resourceWaiters
  -> TimePolicy=ContinueWorld，所以 WorldClock 继续

下一次真实 Tick 的目标约为 09:13:20
  WorldDriver 先停在边界 09:12
  -> TaskManager 精确取出 B
  -> B 通过 TriggerGate
  -> ResourceArbiter 判定与 story:main 不冲突
  -> StartGate 检查 09:12 < 09:15，通过
  -> B 立即开始；同步任务直接生成 ChangeSet，异步任务登记自己的 PendingExecution
  -> 处理完 09:12 后，WorldDriver 可继续到 Tick 目标

现实 +3s / 游戏 09:15
  B 已在有效窗口内取得执行权，不会因 A 尚未完成而被过期跳过
  C、D 继续等待 story:main

现实 +6s / 游戏 09:20
  A 的 Promise 完成
  -> ResultCommand -> CommitGate -> SerialCommitQueue
  -> A 提交并 Finalize，释放 story:main
  -> ResourceArbiter 唤醒 C、D
  -> 不需要回头处理 B；B 已在 09:15 前正常启动
```

这正是防吞噬规则：**互斥只跟资源/依赖有关，不跟 TaskSequenceType 绑定。** 若 B 也需要 `story:main`，则四个约束“不可并发、A 不释放、A 不可中断、B 必须 09:15 前开始”互相矛盾，必须显式选择抢占、释放资源、过期或补偿策略。

## 8. 过期与异步迟到

时间边界必须拆开：

- `dueAt`：最早进入 Ready 的时刻；
- `startBefore`：最晚取得执行权；
- `commitBefore`：最晚允许提交结果；
- `activeUntil`：持续效果或 Activity 生命周期终点。

每个边界单独声明 Skip / RunLate / CatchUp / Compensate 等 LatePolicy。真实时间超时与游戏时间 deadline 分开配置。外部异步恢复还要声明 Retry / Reissue / QueryRemote / Cancel / Compensate，存档中不能只留下一个无法恢复的 Promise 状态。

异步 Task 还必须声明因果策略：

- `Independent`：结果不影响等待期间的世界，WorldDriver 可继续。
- `StopWorldUntilResult`：后续世界依赖结果；在发起边界写入 causal barrier / PauseWorld，结果提交后再恢复。
- `AllowLateResult`：世界继续，结果回流后按 commitBefore 与 LatePolicy 处理。
- `UseRecordedResult`：离线 advance / 回放消费已录制 ResultCommand，不访问真实外部服务。

若 15 分 Task E 显式 `dependsOn` 12 分 HTTP A，而 A 使用 ContinueWorld：E 在 15 分进入 dependency waiter；HTTP 到 16 分才回流时，StartGate 会发现 `startBefore=15` 已过，只能 Skip / RunLate / CatchUp / Compensate，不能倒退到 15 分。若 E 必须准时发生，A 必须使用 `StopWorldUntilResult`。

TaskRecord 与 ExecutionRecord 必须分开：一个周期 Task 可同时存在多个 execution。存档需要原子保存 WorldState、WorldClock、真实时间换算余数、TaskRecord、ExecutionRecord、幂等账本和 commitSequence；读档后由权威记录重建两张表及所有等待队列。禁止保存 Promise、函数回调、运行时容器和非确定性 ID。

## 10. advance 与在线 Tick


| 路径              | 行为                                                                 |
| --------------- | ------------------------------------------------------------------ |
| 在线 Tick | `RunningTicker` 提交 Δreal → WorldDriver 计算 target → 逐边界推进 |
| advance(target) | 使用同一循环逐个处理 `nextSettleAt` / PauseWorld / 日边界，直到 target |
| PauseWorld | WorldClock 尚未越过该边界；返回实际 `toTime`，播放器保留剩余 target |


在线与 advance 共用推进引擎，但“状态哈希等价”只保证纯确定性任务或已记录 ResultCommand 的回放。遇到会影响后续世界的未决 HTTP/用户输入时，advance 必须停止或使用带游戏时间戳的录制结果。

核心 `advanceSlice(target, budget)` 保持同步，不 await 业务 Promise，返回：

```text
Completed | Paused | Yielded | AwaitingExternalInput | Faulted
```

可选 `advanceFully()` 返回 Promise，只用于多帧反复调用 advanceSlice 并 `await nextFrame()`，不能用于等待 HTTP Task。每个 slice 同时限制：

- `maxBoundariesPerSlice`：跨多少个不同绝对时间点；达到后正常 Yield；
- `maxExecutionsPerSlice` / `maxMillisecondsPerSlice`：主线程预算；
- `maxSameTimeRounds` / `maxSameTimeExecutions`：同刻 fixpoint 防零延迟死循环；超过后 Faulted，不得静默跳过。

WorldDriver 是稀疏边界推进器：10→16 之间若只有 12、15 有 Task，则走 `10→12→15→16`；只有真实每分钟边界存在时才逐分钟。纯累加周期可按 CatchUp / Coalesce 算周期数，不必逐条执行。

## 11. 与 Activity / 精确触发的关系

行军、拜访等**长期过程**仍推荐 **Activity + revision**（见世界架构）。Task 可以表示：

- 周期结算（生产、日检测）；
- 精确时刻副作用（抵达、离开）—— 可建模为 `settleLevel = Minute` 的单次 Task；
- Active 长周期（20 天 buff、持续占用资源）。

Activity 取消时递增 revision；Task 结算前校验 revision，不一致则跳过。

## 12. 确定性

- 时间触发顺序仅依赖：绝对 nextSettleAt、阶段、priority（数字小先）、持久化 sequence。
- ReadyScheduler 对资源受阻请求执行旁路调度，但选择结果必须由稳定键决定并记录。
- 同步 ChangeSet 按稳定调度顺序进入 SerialCommitQueue。
- HTTP/用户输入等异步结果属于外部输入；回流时分配递增 command/commit sequence 并记录，回放按该序号重放，不能依赖 Promise 恰好先完成。
- 随机流按已记录的 execution / commit 顺序消费；存档保存流状态。
- 游戏时间采用整数 fixed-point 并持久化换算余数。
- Task ID、executionId、sequence 使用持久化单调序号；禁止 `Date.now()` / `Math.random()` 决定回放顺序。

## 14. 当前实现（`assets/src/task`）

任务引擎已经按本方案实现，并由 `scripts/check-task-engine.ts` 覆盖 §13 的任务语义。对应代码：

1. `WorldDriver.advanceSlice` / `advanceByRealSeconds` / `advanceFully` 是唯一推进循环。`RunningTicker` 每秒把真实时间交给它。`advanceFully` 只在 `Yielded` 时等待下一帧。
2. `WorldClock.moveTo` 一次拨到绝对秒，再发 `listen_advanced`。监听器抛错不会把钟面留在中间。旧的 `Tick` 仍会逐级发 `listen_*`，那条路径不执行任务。
3. `ScheduleIndex`：今日分钟表 `0..1439`，未来日表以滚动 epoch 为槽，窗口外进 `OverflowIndex`。窗口还盖得住今天时不重排；滑出窗口才迁回 overflow，再晋升当天。任务改期前会按插入时的槽位摘掉。
4. `TaskPipeline` 对同步任务做触发、开始、资源、依赖、版本化提交。版本冲突重算一次，仍然冲突就拒绝。写入必须带读集。`serialKey` 视为独占资源。处理函数不能再调用推进。
5. 异步任务进入 `Waiting` 并让出调度器。`ExternalWork.complete/fail/abort` 和 `acceptExternalResult` 只写入 `DurableResultInbox`。安全点在边界批次结束之后，按 `commandSequence` 提交。对不上现存或下一次执行编号的结果会丢弃。同一秒的下一次执行使用带序号的新编号。
6. `timeoutGameSeconds` 到期后按 `asyncRecoveryPolicy` 重发、取消或补偿。`QueryRemote` 超时后释放资源，执行仍可接受迟到结果。取消和中止会释放资源。依赖成环、处理函数抛错都会结束这次推进，抛错的任务标为过期。
7. `PauseWorld` 停在当前秒。之后的 `advanceSlice` 会一直停着，直到 `WorldDriver.resumeAfterDecision()`。恢复后的下一次真实秒会继续折算。失败时保住未完成目标，不再追加新的真实秒。`StopWorldUntilResult` 停到结果提交，不需要玩家恢复。
8. 末段不足一个周期时按 `partialSettlementPolicy` 丢弃、按比例缩放写入差值，或改到 `activeUntil` 再结算一次。活动 `revision` 变化后，旧边界标为过期。
9. `captureGame` / `restoreGame` 保存时钟、换算余数、未完成的暂停、任务、执行、收件箱、幂等账本、实体版本和活动 revision。不保存 Promise、直址表和回调。读档后用 `registerType` 按任务 `type` 重新绑定处理函数；`Retry` / `Reissue` 会再发一次。
10. 编号在进程内单调，并随存档里的 `nextEntitySequence` 延续。

仍不属于这套引擎的内容：

1. 槽内有序插入仍是 `O(m)`。位图扫描有 `scanCursor`，最坏仍是 `O(W/32)`。
2. 没有接入真实网络传输。外部请求停在 `ExternalWork`，由业务自己发请求再调用 `complete`。
3. 粮食消耗、行军、拜访和百支军队规模的世界模拟还没有接到任务上。



## 15. 实施顺序（任务引擎部分已落地）

1. **M0：基础修复**：统一单例访问、构造签名、priority、持久化 ID/sequence、整数游戏时间、今日表范围与滚动窗口。

6. **M5：异步与恢复**：ExecutionRecord、PendingExecution、durable ResultInbox、CausalityPolicy、timeout/Abort/retry/recoveryPolicy。
7. **M6：原子存档与回放**：World/Clock/Task/Execution/ResultInbox/去重表同一快照或日志事务，覆盖 T01–T27。

**最终原则：绝对时间边界决定何时发生；TaskSequenceType 只负责分类与排序；显式资源/依赖决定谁等待；Async 让出调度器；版本化 CommitGate 保证状态正确；全局只有提交串行，只有 PauseWorld 停时钟。**
