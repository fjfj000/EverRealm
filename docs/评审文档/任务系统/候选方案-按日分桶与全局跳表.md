# 候选方案：按日分桶与全局跳表

> 状态：历史选型分析。按日分桶已经演进为滚动日直址表 + 今日分钟表 + overflow，并在任务引擎里实现。最终职责与算法见[游戏任务系统最终方案](游戏任务系统最终方案.md)和[任务队列数据结构评审](任务队列数据结构评审.md)。

本文保留 Map 分桶、跳表等早期候选的比较过程。当前基线不是下文示例里的 `Map<dayId, DayTaskList>`，而是滚动日直址表 + 今日分钟直址表 + overflow；WorldDriver 按绝对 `nextSettleAt` 统一推进，分级时钟事件不参与权威调度。

---

## 1. 需求背景

### 1.1 业务场景

沙盒游戏世界存在大量定时事件，事件需要统一入队调度；游戏以**游戏天**为周期批量触发事件：每到新的游戏日，取出队列内**当天触发的全部事件**，按照指定规则有序依次执行。

- 事件触发依据：`StartTime`（事件开始时间）
- 触发周期：按游戏天批量触发
- 高频操作：**事件插入（高频）**
- 批量操作：每日定时范围遍历、取出当日所有事件、按序执行
- 附加能力：支持事件取消（删除指定事件）

### 1.2 事件排序规则

比较函数（三元组优先级）：

1. 第一关键字：`StartTime` 升序（时间越早越优先）
2. 第二关键字：`SequenceType` 升序
3. 第三关键字：`Priority` 升序

```typescript
private _compareTask(a: TaskBase, b: TaskBase): number {
    if (a.StartTime !== b.StartTime) {
        return a.StartTime - b.StartTime;
    }
    if (a.SequenceType !== b.SequenceType) {
        return a.SequenceType - b.SequenceType;
    }
    return a.Priority - b.Priority;
}
```

### 1.3 约束与痛点

1. 事件时间可以分布在很多个游戏天，时间范围很大，**不适合固定大小静态桶**；
2. 需要批量取出**一个时间区间内全部有序事件**，不是只获取最近单个事件；
3. 沙盒长期运行，事件会持续累积，需要规避插入、遍历的性能退化；
4. 支持后续扩展：事件取消、任意时间段范围查询。

## 2. 候选方案评估

> 约定：n = 全局事件总数；m = 单分组内事件数量；k = 命中查询条件的事件数量

| 方案 | 插入复杂度 | 范围查询（当日事件） | 优点 | 缺点 | 适配评估 |
| --- | --- | --- | --- | --- | --- |
| 最小堆 | $O(\log n)$ | $O(k\log n)$ | 实现简单，获取全局最小值快 | 堆不支持范围查询；批量取区间事件需要反复 pop + 临时备份、回压，逻辑繁琐、性能差，新增插入容易破坏备份状态 | ❌ 不推荐 |
| 全局有序数组 + 二分查找边界 | 插入 $O(n)$，查询 $O(\log n + k)$ | $O(\log n + k)$ | 查询区间速度快，迭代天然有序 | 插入需要数组移位，高频插入、事件量大时容易卡顿 | ❌ 仅适合极小事件量，沙盒长期运行不适用 |
| 全局有序平衡树 / 跳表（TreeSet） | $O(\log n)$ | $O(\log n + k)$ | 通用时间线结构；支持任意时间范围查询、顺序迭代、删除；迭代到区间终点自动停止 | TS 原生无实现，需要自行封装跳表/平衡树，实现成本更高 | ✅ 通用备选（适合跨天事件、任意时间窗口查询） |
| **按游戏天分桶 + 桶内有序容器（推荐方案）** | 桶内二分有序数组：$O(m)$；桶内跳表：$O(\log m)$ | $O(k)$ | 业务语义完美匹配；事件按天隔离，互不干扰；查询当日事件直接取对应分组，遍历开销低；调试简单、易排查单日事件；压力分散到每一天 | 前提：事件触发时间点归属唯一游戏天，不支持单事件跨多天持续触发 | ✅✅ 首选工程方案 |

> **核心结论：**
> - 如果事件仅在归属的游戏天触发、无跨多天持续事件：优先选择【按游戏天分桶方案】，开发成本低、性能优秀、贴合业务；
> - 如果存在跨天事件、需要灵活查询任意时间段事件：选择【全局跳表有序集合方案】；
> - 最小堆不适合本场景，堆的优势是逐个拿最近事件，不适合定期批量捞出一段时间窗口的事件。

## 3. 方案A：按游戏天分桶方案（推荐）

### 3.1 设计思路

1. **转换函数**：通过 `StartTime` 换算出归属的游戏天编号 `dayId`

```typescript
function getDayId(startTime: number): number {
    // DAY_DURATION：单个游戏天的时间长度，单位与 StartTime 保持一致
    return Math.floor(startTime / DAY_DURATION);
}
```

2. **顶层存储**：`Map<dayId, DayTaskList>`
    - key：游戏天编号 dayId
    - value：`DayTaskList`，保存当天所有事件，内部维持三元组有序

3. **流程**：
    - 插入事件：计算 dayId，放入对应天的有序列表，维持排序；不存在该天分组则新建；
    - 每日触发：根据当前 dayId 获取对应分组，一次性取出全部有序事件，遍历执行；执行完成后销毁该天分组；
    - 取消事件：定位到对应 dayId 的分组，在组内删除目标事件。

### 3.2 适用边界

- ✅ 适合：事件触发时刻属于唯一一天，事件不会跨多天持续触发；沙盒每日批量调度。
- ❌ 不适合：单个事件需要在连续多个游戏天都生效触发。

### 3.3 源码骨架

```typescript
type TaskCompareFn = (a: TaskBase, b: TaskBase) => number;
const DAY_DURATION = 86400; // 游戏一天时长，和 StartTime 单位对齐

function getDayId(time: number): number {
    return Math.floor(time / DAY_DURATION);
}

/** 单日事件有序容器：二分有序数组，适合单日事件数量中等规模 */
class DayTaskList {
    private _list: TaskBase[] = [];
    private _compare: TaskCompareFn;

    constructor(cmp: TaskCompareFn) {
        this._compare = cmp;
    }

    insert(task: TaskBase) {
        let l = 0, r = this._list.length;
        while (l < r) {
            const mid = (l + r) >> 1;
            if (this._compare(task, this._list[mid]) < 0) {
                r = mid;
            } else {
                l = mid + 1;
            }
        }
        this._list.splice(l, 0, task);
    }

    takeAll(): TaskBase[] {
        const res = [...this._list];
        this._list.length = 0;
        return res;
    }

    remove(task: TaskBase) {
        const idx = this._list.indexOf(task);
        if (idx >= 0) {
            this._list.splice(idx, 1);
        }
    }
}

export class SandboxTaskQueue {
    private readonly _dayMap = new Map<number, DayTaskList>();
    private readonly _compare: TaskCompareFn = (a, b) => {
        if (a.StartTime !== b.StartTime) return a.StartTime - b.StartTime;
        if (a.SequenceType !== b.SequenceType) return a.SequenceType - b.SequenceType;
        return a.Priority - b.Priority;
    };

    insert(task: TaskBase) {
        const dayId = getDayId(task.StartTime);
        if (!this._dayMap.has(dayId)) {
            this._dayMap.set(dayId, new DayTaskList(this._compare));
        }
        this._dayMap.get(dayId)!.insert(task);
    }

    takeDayTasks(dayId: number): TaskBase[] {
        const list = this._dayMap.get(dayId);
        if (!list) return [];
        const tasks = list.takeAll();
        this._dayMap.delete(dayId);
        return tasks;
    }
}
```

> **优化提示**：当单日事件数量很大（上千条），将 `DayTaskList` 内部实现替换为跳表，把组内插入复杂度从 $O(m)$ 降低至 $O(\log m)$。

## 4. 方案B：全局跳表有序集合（通用时间线方案）

### 4.1 设计思路

1. 所有事件放入同一个全局有序跳表，排序键为三元组 `(StartTime, SequenceType, Priority)`；
2. 每日触发时：
   - 使用当日起始时间作为下界，在跳表中定位迭代起点；
   - 顺序向后迭代收集事件，一旦事件 `StartTime` 超过当日结束时间，终止迭代；
   - 收集到的事件天然有序；取出后从集合删除。

### 4.2 适用边界

- ✅ 适合：存在跨多天生效事件、需要支持任意自定义时间窗口查询、灵活的事件调度系统。
- ❌ 缺点：实现复杂度更高，需要自行实现支持自定义比较器、范围迭代、删除的跳表。

---

## 5. 补充优化建议（沙盒游戏常用）

1. **延迟删除标记**：高频取消事件场景，不立刻 splice 删除，打上删除标记，在每日遍历触发时过滤掉标记事件，避免数组频繁移位卡顿；
2. **内存回收**：久远的过去游戏天事件如果已经不会再触发，可以主动清理对应分组；
3. **监控埋点**：统计每日事件数量、插入耗时，用于性能监控，判断是否需要升级为跳表实现。
