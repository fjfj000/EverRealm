# 文字沙盒战争游戏：技术架构与实施规划

> **文档版本：** v1.0\
> **技术方向：** TypeScript、模块化单体、事件驱动模拟、纯程序 AI\
> **游戏定位：**
> 以军队与战争为核心、个人冒险为入口、势力演化为长期驱动力的文字沙盒游戏

## 1. 项目目标

设计一款参考《骑马与砍杀》沙盒体验的文字游戏。玩家通过菜单与自由文字混合操作，管理个人、军队和势力；世界中的
NPC、战斗与经济系统完全由程序规则驱动，不依赖 LLM。

### 1.1 核心玩法闭环

探索世界 → 选择发展方向 → 积累资源并培养队伍 → 参与战斗或政治行动 →
获得财富、声望、关系或领土 → 世界持续演化。

### 1.2 三个游戏尺度

1.  **个人冒险：** 探索、任务、装备、人物互动。
2.  **军队与战场：** 招募、训练、编队、行军、侦察、伏击、攻城。
3.  **世界与势力：** 战争、城镇生产、商队贸易、领土变化。

核心原则：**所有重要行为最终都作用于统一的世界状态。**

### 1.3 已确定的设计选择

-   玩家体验：综合型，兼顾个人成长、军队指挥与世界演化。
-   世界运行：在线 Tick 与 `advance` 共用 WorldDriver 的绝对时间边界循环；`listen_*` 仅作派生通知。TaskSequenceType 不承担互斥，显式资源/依赖决定等待。细节以 `docs/世界架构/` 与任务系统最终方案为准。
-   战斗模拟：分阶段战斗。
-   战场单位：小队级，不逐个模拟所有士兵。
-   玩家输入：菜单 + 自由文字。
-   敌方 AI：纯程序实现，不依赖 LLM。
-   技术架构：优先采用 TypeScript 模块化单体，早期不拆微服务。

## 2. 总体技术架构

``` text
Presentation（表现层）
  ├─ 菜单与交互
  ├─ 自由文字指令入口
  └─ 叙事文本、战报与事件日志
          ↓
Application（应用层）
  ├─ 指令解析与参数补全
  ├─ 行动校验与编排
  ├─ 状态查询
  └─ 存档服务
          ↓
Simulation（模拟层）
  ├─ 播放器（真实时间 × 速率）
  ├─ WorldDriver 同步切片与推进预算（Tick + advance）
  ├─ Task ScheduleIndex（滚动日表 + 今日分钟表 + overflow）
  ├─ TaskPipeline（ReadyScheduler、ResourceArbiter、ExecutionRecord、ResultInbox、版本化提交）
  ├─ 战略 AI
  ├─ 战斗引擎与战术 AI
  └─ 经济、补给与战争模拟
          ↓
Domain（领域层）
  ├─ 世界状态与实体
  ├─ 游戏规则
  └─ 状态变更与领域事件
          ↓
Persistence（持久化层）
  ├─ 存档与读档
  └─ 可选的事件日志、回放记录
```

### 2.1 架构约束

-   AI 只能提出行动意图，不能直接修改世界状态。
-   所有行动由统一执行器校验后执行。
-   表现层不能直接修改领域状态。
-   战略地图与战场使用不同的坐标和数据模型。
-   游戏时间推进必须经过统一时间引擎。
-   随机数状态应进入存档，以支持确定性回放。
-   AI 只能根据其可观察到的信息做决策，避免读取全部隐藏信息。

## 3. 核心领域模型

### 3.1 世界状态

权威时间是累计游戏秒，Task 最低结算粒度是分钟。权威世界状态放在 `WorldState`；TaskRecord 单独持久化，运行时按 `nextSettleAt` 重建按日总表和今日分钟表。

字段、锚点和存档 DTO 以 `docs/世界架构/数据结构.md` 为准。存档要保存随机流的完整状态、待处理事件、下一档结算时间和未完成的阻塞决定。实体 ID 使用存档中的递增序号。

### 3.2 人物、兵力与队伍

-   **Character：** 人物属性、技能、健康、关系等，主要用于玩家、重要 NPC
    和需要单独交互的人物。
-   **TroopStack：** 兵种
    ID、数量、经验、装备等级等。普通士兵以数量堆叠管理，不逐个创建
    Character。
-   **Party：**
    战略地图上的队伍，包含当前节点、兵力、补给和所属势力。行军路线写在行军活动上，不在队伍上再存一份。
-   **BattleUnit：**
    进入战斗后展开的小队单位，包含战场位置、命令、士气、疲劳、队形完整度、弹药及状态。

进入战斗时，将战略队伍中的兵力按兵种和编组规则展开成
BattleUnit；战斗结束后，将伤亡、经验、士气和补给变化同步回战略队伍。战略地图坐标和战场坐标必须分离。

### 3.3 战斗实体

``` ts
type BattlePhase =
  | "deployment"
  | "command"
  | "movement"
  | "combat"
  | "morale"
  | "resolution"
  | "finished";

interface Battle {
  id: EntityId;
  phase: BattlePhase;
  round: number;
  attackerPartyId: EntityId;
  defenderPartyId: EntityId;
  units: Record<EntityId, BattleUnit>;
  terrainId: string;
  startedAt: GameTime;
}
```

战斗由阶段状态机驱动。战斗回合与世界时间是两个不同概念；可以为战斗阶段配置时间消耗，但不能直接把回合数等同于世界分钟数。

### 3.4 事件模型

事件使用判别联合类型。排序键是 `dueTime` 升序、`priority` 升序、`sequence` 升序。数字小的优先级先执行。

时钟驱动：Task 系统对每段 `(from, to]` 结算。`taskIntervalMinutes` 默认 1440，作为日检测 cadence 参考。精确时刻与日检测均为 Task 边界类型（详见 `docs/评审文档/任务系统/`）。

-   **精确边界：** 抵达、离开、断粮、战斗阶段、PauseWorld 决定。
-   **日检测：** 生产、税收、军饷、英雄刷新、无法预测的相遇、常规战略评估。不扣行军粮食。

活动版本不符的事件到期后跳过。队伍改道后，旧的抵达事件不能再更新位置。完整定义见 `docs/世界架构/数据结构.md`。

## 4. 世界时间与推进

规范循环在 `docs/世界架构/开发与验收.md`。这里只保留全项目需要一致的规则。

### 4.1 时间原则

权威时间为累计游戏秒（`TotalGameTime`）；显示层再换成小时和日期。Task 最低结算粒度为游戏分钟。

-   播放器把真实增量或离线目标交给 WorldDriver；WorldClock 只被 Driver 原子推进。默认 1 真实秒 = 100 游戏秒。
-   时钟持续推进；**Waiting 默认不停世界**；仅 **PauseWorld**（及玩家速率 0）停止时间前进。
-   Tick 与 `advance` 共用 `nextSettleAt / 日边界 / PauseWorld` 的统一循环；分级监听不参与权威调度。
-   核心 `advanceSlice` 同步且不等待业务 Promise；达到边界/执行/毫秒预算返回 Yielded，异步 `advanceFully` 只负责跨帧续跑。
-   粮食和行军用锚点与整数余数；分段与一次 advance 结果必须相同。
-   NPC 在日检测做常规评估；紧急评估每个势力同时最多一条。

### 4.2 推进流程

见 `docs/世界架构/开发与验收.md` §5：绝对边界 → TaskExecutionRequest → ReadyScheduler → ResourceArbiter/DependencyGraph → 三段校验 → Sync/Async Executor → DurableResultInbox → 版本化串行提交。ContinueWorld 下迟到依赖走 LatePolicy；必须准时的外部结果使用 StopWorldUntilResult。

### 4.3 中途遭遇与行动中断

行军按下一节点排边界。可算相遇排精确 Task；否则由日检测发现。拜访离开为 ContinueWorld；需立即选择为 PauseWorld。

离线 `advance` 遇 PauseWorld 即停，不一次性结算未参与的决定之后的状态。

### 4.4 同时刻边界与重复处理

-   检查 activity revision 与终态；幂等终态。
-   注册新边界，不嵌套区间结算。
-   过期边界按 Task 策略跳过，**不阻断**同段内其他 Task。

## 5. 战斗引擎

### 5.1 分阶段战斗流程

建议固定每轮处理顺序：

1.  锁定本轮命令与战场快照。
2.  更新战场信息。
3.  战术 AI 生成命令。
4.  校验命令合法性。
5.  执行小队移动和阵型调整。
6.  结算远程攻击。
7.  结算近战攻击。
8.  更新伤亡、疲劳、士气和队形。
9.  判断溃逃或撤退。
10. 判断战斗是否结束。
11. 生成战报并进入下一轮。

每轮采用一致的状态快照和结算顺序，避免单位更新先后顺序意外影响结果。

### 5.2 小队战斗模型

小队是战场的主要计算单位。每个小队由同兵种或相近兵种的士兵构成，并具有数量、战斗属性、士气和阵型等数据。

初期可以采用聚合战斗力模型：

\[ A\_{`\text{squad}`{=tex}} = `\sum`{=tex}\_i N_i `\cdot `{=tex}A_i
`\cdot `{=tex}E_i `\cdot `{=tex}F_i \]

其中：

-   (N_i)：对应兵种的有效人数。
-   (A_i)：攻击属性。
-   (E_i)：经验或训练系数。
-   (F_i)：疲劳、状态等修正系数。

伤害还应考虑防御、护甲、距离、地形、阵型和兵种克制。例如：

\[ D = `\max`{=tex}(0, A-B) `\cdot `{=tex}M\_{`\text{terrain}`{=tex}}
`\cdot `{=tex}M\_{`\text{formation}`{=tex}}
`\cdot `{=tex}M\_{`\text{counter}`{=tex}} \]

以上公式只用于原型，不是最终平衡方案。需要避免防御值导致伤害长期为零，也要防止乘数叠加造成伤害失控。参数应通过批量模拟校准。

### 5.3 兵种标签

建议通过数据驱动的兵种配置和标签表达能力，例如：

-   `anti-cavalry`：反骑。
-   `ranged`：远程攻击。
-   `shielded`：持盾。
-   `cavalry`：骑兵。
-   `heavy-armor`：重甲。
-   `skirmisher`：散兵。

AI 和战斗规则优先读取标签与属性，避免按具体兵种 ID 大量编写特判。

### 5.4 士气与溃逃

士气可用 0--100 表示，以下阈值仅作为初期调试参考：

       士气 状态       行为倾向
  --------- ---------- ----------------------------
    70--100 稳定       正常执行命令
     40--69 受压       仍能战斗，但更容易受到冲击
     20--39 动摇       可能降低效率或局部失序
      1--19 崩溃边缘   溃逃概率显著上升
          0 溃逃       强制失去组织或退出战斗

士气变化应综合伤亡、侧翼受击、指挥官状态、友军溃逃和战场优势等因素。阈值与概率需要通过模拟测试确定。

### 5.5 战斗结果回写

战斗结束后，将结果统一同步回战略队伍和世界状态：

-   伤亡、受伤和俘虏。
-   经验与训练变化。
-   士气、疲劳和弹药。
-   粮食等补给消耗。
-   俘虏、战利品和声望。
-   队伍是否解散、撤退或被俘。
-   战争、围城和领土控制等后续状态。

## 6. 纯程序 AI

### 6.1 分层结构

**战略 AI** 决定世界地图上的目标：

-   攻城、增援、追击。
-   侦察、劫掠、补给。
-   撤退、避战、集结。
-   根据战争局势重新规划目标。

**战术 AI** 决定战斗中的局部行为：

-   选择阵型。
-   决定推进、固守、包抄或撤退。
-   选择攻击目标。
-   保护弓箭手或薄弱侧翼。
-   根据地形和兵种构成调整战术。

**执行层** 使用有限状态机推进具体动作，例如：

`待命 → 移动 → 接敌 → 攻击 → 重组 → 撤退`

目标选择与动作执行应分离。目标变化时，不应导致正在执行的动作无条件中断。

### 6.2 效用评分

可以使用效用评分选择行动：

\[ Score(a) = w_b Benefit(a) + w_s StrategicValue(a) + w_p
SuccessProbability(a) - w_c Cost(a) - w_r Risk(a) \]

评分项应归一化或使用明确的取值范围，避免不同量纲直接相加导致某一项支配全部决策。

NPC 性格可以调整权重：

-   **好战：** 提高进攻收益权重，降低风险惩罚。
-   **谨慎：** 提高风险惩罚，偏好增援或撤退。
-   **忠诚：** 提高保护所属势力或盟友的价值。
-   **逐利：** 提高劫掠、贸易和战利品收益权重。

性格影响评分权重，而不是直接指定固定行为。

### 6.3 避免目标频繁切换

如果每次评估都选择当前分数最高的目标，NPC
可能在多个目标之间反复横跳。建议使用目标切换滞回：

-   当前目标仍有效时，给予一定持续性加分。
-   新目标必须比当前目标高出指定阈值，才允许切换。
-   目标失效、风险显著变化或出现紧急事件时，可以立即切换。

### 6.4 AI 观察数据与防作弊

建议为 AI 提供受限的观察数据，而不是直接暴露完整 `WorldState`：

``` ts
interface Observation {
  visiblePartyIds: EntityId[];
  knownEnemyStrength: Record<EntityId, number>;
  visibleSettlementIds: EntityId[];
  confidence: Record<EntityId, number>;
}
```

情报可以包含准确度、过期时间和来源，AI 应根据不确定性做决策。

### 6.5 决策接口与行动提案

``` ts
interface DecisionContext {
  world: Readonly<WorldState>;
  actorId: EntityId;
  now: GameTime;
}

interface DecisionResult<TAction> {
  action: TAction;
  reasonCode: string;
  score?: number;
}

interface DecisionPolicy<TAction> {
  decide(context: DecisionContext): DecisionResult<TAction> | null;
}
```

实际项目中，建议将完整 `world` 替换为受限的 `Observation`
与必要的只读上下文。

AI 产出的动作统一表示为
`ActionProposal`。行动执行器负责检查前置条件、资源、路径、权限和当前状态，再执行动作并修改世界状态。被拒绝的动作要记录原因，便于调试。

## 7. 玩家交互：菜单与自由文字

### 7.1 统一命令模型

菜单和自然语言输入最终都转换成结构化的
`PlayerCommand`，再复用相同的校验与执行流程。

``` ts
type PlayerCommand =
  | { type: "move"; targetId: EntityId }
  | { type: "recruit"; troopTypeId: string; count: number }
  | { type: "attack"; targetPartyId: EntityId }
  | { type: "inspect"; targetId: EntityId };
```

### 7.2 指令解析器职责

1.  关键词与别名识别。
2.  实体名称识别。
3.  意图分类。
4.  参数提取与补全。
5.  检查歧义并请求玩家确认。
6.  输出结构化命令，不直接执行命令。

例如，"攻打北面的城堡"如果对应两个可能目标，应询问玩家选择哪个，而不是自行猜测。

### 7.3 行动执行流程

`解析 → 等当前区间结算返回 → 校验前置条件 → 计算耗时与成本 → 必要时确认风险 → 修改活动并注册 Task 边界 → 播放器继续 Tick/advance → 输出结果`

要求：

-   校验失败不能扣资源或推进时间。
-   执行中出现遭遇时，应暂停并保存原行动上下文。
-   战后检查原行动是否仍然合法，再决定是否继续。
-   重要行动记录结果、成本、时间和失败原因。

## 8. 经济、补给与世界模拟

经济与补给是影响战略选择的约束，而不是独立的背景数值。逐步实现：

-   工资与军队维护。
-   粮食消耗、补给库存和断粮惩罚。
-   城镇生产、税收与资源流动。
-   商队移动和贸易。
-   招募、训练、装备与经验成长。
-   战争状态、围城和领土控制。

任务检测以可配置的一天为最小间隔：

-   当天的精确事件：抵达、离开、断粮、战斗阶段、阻塞决定。
-   当天的检测：生产、税收、军饷、英雄刷新、无法预测的相遇、常规战略评估。

行军粮食按锚点扣除。断粮时刻落在今天就在今天激活，落在以后的天就留到那一天。当日检测不再扣同一份粮。

## 9. 存档、确定性与调试

### 9.1 确定性回放

相同初始状态、随机数状态和命令序列，在相同规则版本下应得到相同结果。为此需要：

-   保存伪随机数生成器状态。
-   明确事件排序规则。
-   避免依赖不稳定的对象遍历顺序。
-   固定战斗阶段的结算顺序。
-   为重要状态变化记录原因和来源。
-   为存档版本升级提供迁移策略。

### 9.2 日志与决策解释

建议记录：

-   NPC 评估的候选目标。
-   各候选目标的评分与关键因素。
-   最终选择的动作及 `reasonCode`。
-   行动被拒绝的原因。
-   事件被忽略的原因，例如过期或目标状态已改变。
-   战斗伤亡、士气变化和结束条件。

这些日志既服务开发调试，也可以转化为游戏内战报和叙事素材。

建议先保持模块化单体。只有在性能、部署或团队协作确实需要时，再考虑拆分服务。

## 11. MVP 分阶段实施

### M1：世界状态与时间引擎

**实现内容：**

-   核心实体、活动与统一世界状态。
-   按日总表、今日分钟表、日切晋升和稳定槽内排序。
-   TaskPipeline：ScheduleIndex、ReadyScheduler、资源/依赖、ExecutionRecord 与三段 Gate 分责；提交带版本校验。
-   Tick + advance 共用绝对边界循环、锚点结算、精确 PauseWorld 和重入拒绝。
-   播放器的速率换算与离线补时。
-   存档、读档和随机流恢复。

**验收标准：**

-   相同初始状态与命令序列产生相同结果。
-   不漏执行、不重复执行当天的有效事件，也不激活其他天的任务。
-   版本不符的事件不会改变世界状态。
-   分段推进和一次性推进在相同规则下结果一致。
-   阻塞决定会停住游戏时间；非阻塞拜访会在离开事件到期后结束。

### M2：小队战斗引擎

-   兵种和小队数据。
-   战场部署与单位移动。
-   远程、近战攻击结算。
-   伤亡、士气和战斗阶段状态机。
-   战果同步回战略队伍。

### M3：战术 AI

-   基于效用评分的目标与命令选择。
-   步兵、弓箭手、骑兵的基础行为。
-   阵型、撤退和溃逃。
-   决策日志与可复现测试。

### M4：世界模拟与战略 AI

-   军队移动、追击和遭遇。
-   NPC 目标选择与重新规划。
-   补给、战争、围城和领土控制。
-   途中事件打断和行动恢复。

### M5：经济与玩家成长

-   招募、工资、粮食。
-   装备、经验和声望。
-   城镇收入与生产。
-   基础交易和资源循环。

### M6：交互与平衡

-   菜单与自由文字指令。
-   实体歧义确认与参数补全。
-   批量战斗模拟与长期世界模拟。
-   数值平衡、性能优化和用户体验完善。

### 11.1 MVP 建议规模

初始测试世界可从以下规模起步：

-   1 张小型战略地图。
-   3 个势力。
-   5--10 个城镇或城堡。
-   20--30 支 NPC 队伍。
-   6--8 种基础兵种。

这些是控制初期复杂度的建议，不是最终规模限制。

## 12. 自动化测试与平衡验证

### 12.1 规则单元测试

覆盖伤害、护甲、士气、补给、移动时间和行动前置条件等基础规则。

### 12.2 确定性回放测试

固定初始存档、随机数种子和玩家命令，验证多次运行的结果一致。

### 12.3 战斗批量模拟

批量运行不同兵种、兵力、地形、阵型和指挥策略的对战，观察胜率、伤亡、战斗时长与溃逃情况。不要只凭少数手工战斗判断平衡。

### 12.4 长期世界模拟

持续模拟 100--365 个游戏日，检查：

-   势力是否无故灭绝或永久僵持。
-   NPC 是否陷入反复移动或目标切换。
-   经济是否崩溃或资源无限膨胀。
-   队伍是否长期断粮却不采取行动。
-   总表/今日表是否不断积压，stale 候选比例是否异常。
-   是否出现重复结算、负数资源或非法状态。
-   世界是否能持续产生有意义的变化。

## 13. 首个可运行闭环

建议先实现一条规模很小但完整的流程：

1.  玩家队伍在战略地图移动。
2.  时间引擎推进到途中事件。
3.  触发敌军遭遇。
4.  双方队伍展开为战场小队。
5.  玩家选择战术，敌方由程序 AI 决策。
6.  战斗引擎逐阶段结算。
7.  更新伤亡、士气与补给成本。
8.  战果同步回战略队伍。
9.  世界时间继续推进，后续事件重新安排。
10. 保存状态并输出战报。

这条闭环可靠后，个人成长、城镇经营、外交和战争系统都可以逐步接入统一世界状态与行动执行机制。

## 14. 关键风险与控制措施

1.  **AI 不能直接修改状态：** 由行动执行器统一校验和提交，保证规则一致。
2.  **战斗回合不等于世界时间：** 明确二者的转换规则。
3.  **一次推进只处理当前这一天：** 提前执行以后的任务，或在同一天里跳过已到期的任务，都会打乱遭遇、断粮和抵达的顺序。
4.  **避免逐个模拟普通士兵：** 优先使用小队和兵种数量聚合。
5.  **减少兵种 ID 特判：** 优先采用数据、标签和可配置规则。
6.  **避免 NPC 每回合无条件重规划：**
    采用事件触发、评估周期和目标切换滞回。
7.  **不能只靠手工试玩平衡：** 建立批量战斗和长期世界模拟。
8.  **不要过早拆微服务：** 先做好领域边界与状态一致性。

## 附录 A：推荐开发顺序

1.  `WorldState`、实体 ID、随机数管理。
2.  整数 WorldClock、WorldDriver、Task 两级 ScheduleIndex 与安全 TaskPipeline。
3.  行动校验器和状态变更入口。
4.  最小 `BattleEngine`。
5.  最小 `TacticalAI`。
6.  战斗结果回写与存档回放。
7.  战略地图移动与遭遇事件。
8.  战略 AI、经济与补给。
9.  菜单和自由文字输入。
10. 批量模拟、平衡和内容扩充。

## 附录 B：模块完成标准

一个模块不仅要"能运行"，还应满足：

-   有明确输入和输出。
-   不绕过统一规则直接修改其他模块状态。
-   有单元测试或模拟测试。
-   重要状态变化有日志。
-   能在固定初始条件下复现问题。
-   失败时不会留下半完成的资源扣除或时间推进。
-   有可量化的验收标准。
