# 数据结构

## 1. 设计原则

数据结构需要服务于世界模拟、事件调度、纯程序 AI、存档和调试。核心原则：

1.  权威状态与查询索引分离。
2.  实体之间通过 ID 关联，避免深层嵌套。
3.  AI 决策与状态修改分离。
4.  当前状态、未来事件、历史记录分离。
5.  运行时结构与存档 DTO 分离。
6.  先选择简单可靠的结构，再通过性能测试优化。

## 2. 核心类型与 WorldState

``` ts
type EntityId = string;
type GameTime = number; // 整数分钟
type EventId = string;
type ResourceId = string;
type MapNodeId = EntityId;

interface WorldState {
  schemaVersion: number;
  currentTime: GameTime;
  taskIntervalMinutes: number;
  nextEntitySequence: number;
  nextEventSequence: number;
  rngStates: Record<string, RngSnapshot>;
  playerId: EntityId;
  pendingDecision: PendingDecision | null;

  characters: Map<EntityId, Character>;
  parties: Map<EntityId, Party>;
  settlements: Map<EntityId, Settlement>;
  factions: Map<EntityId, Faction>;
  battles: Map<EntityId, Battle>;
  wars: Map<EntityId, War>;
  activities: Map<EntityId, Activity>;
}
```

### 为什么用 `Map<EntityId, Entity>`？

-   按 ID 查询的平均时间复杂度通常为 `O(1)`。
-   实体之间通过 ID 关联，降低深层嵌套和循环引用。
-   迁移实体归属更容易。
-   查询索引可以从权威实体重建。

`Map` 不适合所有条件查询。按 ID 查实体用
`Map`；按势力、位置或状态查找则建立专门索引。存档时需将 `Map`
转为可序列化 DTO，不能直接依赖 `JSON.stringify()` 序列化其条目。

待处理 Task 与 PendingExecution 不属于 `WorldState` 实体表；Task 权威记录单独持久化，运行时按 `nextSettleAt` 放进 `_tasks` / `_todayTasks` 两级直址表。`pendingDecision` 表示 **PauseWorld** 未决，播放器在 advance 路径上不能越过该时刻，直至玩家命令清空。

`taskIntervalMinutes` 是一天的长度，默认 1440，可配置并写入存档。日检测 Task 的 cadence 参考该值；**区间结算**按 `(from, to]` 与各 Task 边界处理，而非“一次只激活一个检测区间”。

## 3. 核心实体

### 3.1 人物

``` ts
interface Character {
  id: EntityId;
  name: string;
  factionId?: EntityId;
  partyId?: EntityId;
  skills: Record<string, number>;
  health: number;
  morale: number;
  relationshipIds: EntityId[];
  traits: string[];
}
```

普通士兵通常不必逐个建 `Character`。将领、重要 NPC
或具有独立关系与剧情的人物才需要独立实体。

### 3.2 战略军队与兵力编组

``` ts
interface Party {
  id: EntityId;
  factionId: EntityId;
  locationId: MapNodeId;
  troopStacks: TroopStack[];
  food: AnchoredQuantity;
  gold: number;
  morale: number;
  activityId?: EntityId;
  activeBattleId?: EntityId;
}

interface TroopStack {
  troopTypeId: string;
  count: number;
  experience: number;
  equipmentTier: number;
}

interface AnchoredQuantity {
  value: number;
  remainder: number;
  anchoredAt: GameTime;
  rateNumerator: number;
  rateDenominator: number;
}

interface MarchActivityData {
  route: MapNodeId[];
  segmentIndex: number;
  speedPerMinute: number;
}
```

`TroopStack` 表示战略层兵力聚合；`BattleUnit`
表示战场小队。不要把两种状态混成同一个接口。

`locationId` 是队伍当前所在节点。行军路线放在行军活动的 `MarchActivityData` 里，不在队伍上再存一份移动计划。`food` 用锚点保存，日结算不从这里重复扣除。

### 3.3 城镇与势力

``` ts
interface Settlement {
  id: EntityId;
  name: string;
  factionId: EntityId;
  population: number;
  gold: number;
  food: number;
  materials: Record<string, number>;
  prosperity: number;
  security: number;
  garrisonPartyIds: EntityId[];
}

interface Faction {
  id: EntityId;
  name: string;
  rulerId: EntityId;
  treasury: number;
  policies: string[];
  strategicGoal?: StrategicGoal;
}
```

实体保存当前状态；税收公式、生产规则、战略逻辑放在系统中。队伍和城镇上的 `factionId` 是归属的权威事实。按势力枚举队伍或城镇时走索引，不在势力上再存一份 ID 列表。城镇的 `food` 是库存，由当日检测增减；它和队伍行军口粮不是同一份数量。

## 4. Task 边界、事件结构与调度器

权威时间源为 `WorldClock.TotalGameTime`。WorldDriver 按统一绝对 `nextSettleAt` / 日边界 / PauseWorld 逐点推进；`listen_min/hour/day/month/year` 只作派生通知。TaskManager 用未来日表 + 今日分钟表 + overflow 产出到期候选。详见 `docs/评审文档/任务系统/任务队列数据结构评审.md`。

实现过渡期可保留 `WorldEvent` 命名。`blocking` 字段语义不足，应拆成 `ExecutionMode` 与 `TimePolicy`；资源互斥使用 `resourceClaims/serialKey`，业务依赖使用 `dependsOn`，不能用 Task 类型或队列分组代替。

### 4.1 判别联合类型（精确时刻 / 兼容 DTO）

``` ts
interface EventBase {
  id: EventId;
  dueTime: GameTime;
  priority: number;
  sequence: number;
  blocking: boolean;
  activityId?: EntityId;
  activityRevision?: number;
}

type WorldEvent =
  | (EventBase & { type: "DAY_TICK" })
  | (EventBase & {
      type: "PARTY_ARRIVED";
      payload: { partyId: EntityId; nodeId: MapNodeId };
    })
  | (EventBase & {
      type: "ACTIVITY_DEADLINE";
      payload: { activityId: EntityId };
    })
  | (EventBase & {
      type: "FOOD_EXHAUSTED";
      payload: { partyId: EntityId };
    })
  | (EventBase & {
      type: "BATTLE_PHASE_END";
      payload: { battleId: EntityId; phaseVersion: number };
    })
  | (EventBase & {
      type: "NPC_REEVALUATE";
      payload: { factionId: EntityId };
    });
```

优点：事件类型决定 payload
形状，编译器可检查字段，新增事件可做穷尽检查，减少运行时错误。

`blocking` 是遗留字段，无法无损表达 Async、资源互斥和 PauseWorld，迁移时必须按 Task 类型显式配置。优先级方向需全工程统一；完全同键由持久化 sequence 保序。

边界是否在本次 `(from, to]` 处理，看 `dueTime`（或 settle 时刻）是否落在开闭区间 `(from, to]`，而非“只激活当天”的硬截断。过期边界按 Task 类型 **ExpirePolicy** 跳过或补偿。

### 4.2 事件状态

``` ts
type EventStatus =
  | "pending"
  | "processing"
  | "completed"
  | "cancelled"
  | "stale";
```

不要把"已出队"和"已取消"共用一个状态。

### 4.3 两级 Task 调度接口

``` ts
interface TaskScheduleIndex {
  schedule(task: TaskRecord): void;
  remove(task: TaskRecord): boolean;
  peekNextDueAt(): GameTime | undefined;
  drainAt(dueAt: GameTime): TaskRecord[];
  promoteDay(absoluteGameDay: number): void;
  advanceEpoch(absoluteGameDay: number): void;
  rebuild(tasks: readonly TaskRecord[], now: GameTime): void;
}

interface TaskReadyScheduler {
  enqueue(request: TaskExecutionRequest): void;
  /** 受阻队头要移入 waiters，继续寻找后续可运行请求。 */
  takeRunnable(
    resources: TaskResourceArbiter,
    dependencies: TaskDependencyGraph
  ): TaskExecutionRequest | undefined;
}

interface TaskResourceArbiter {
  tryAcquire(execution: TaskExecutionRecord): boolean;
  release(executionId: string): void;
}

interface TaskDependencyGraph {
  add(execution: TaskExecutionRecord): void;
  rejectCycles(): void;
  notifyFinished(executionId: string): void;
}
```

运行时实现：

- `FutureDayTable = DirectAddressTable<TaskRecord>`：unit 为滚动 epoch 下的游戏日。
- `TodayMinuteTable = DirectAddressTable<TaskRecord>`：unit 为日内分钟 `0..1439`。
- `OverflowIndex`：保存当前直址窗口外的未来 Task。
- `TaskRecord.nextSettleAt` 是索引键；`StartTime` 保持生命周期起点，不因重复结算而改写。
- 同槽顺序：绝对 `nextSettleAt`、阶段、统一方向的 priority、持久化 sequence。

ScheduleIndex 只产出到期候选。TaskSequenceType 只分类；ResourceArbiter 与 DependencyGraph 决定等待。TriggerGate、StartGate、CommitGate 分别在三个安全点检查有效性与版本。

直址表的位图和桶不写存档；只保存 TaskRecord，读档后按 `nextSettleAt` 重建。

## 5. 周期任务

``` ts
interface DayTickSchedule {
  nextRunAt: GameTime;
}
```

当日检测的间隔就是 `WorldState.taskIntervalMinutes`，优先级 200。它处理生产、税收、军饷、英雄刷新、无法预测的相遇和常规战略评估。`TaskSettleLevel=Day` 的 execution 经过统一 TaskPipeline 后，由 Finalizer 更新 `nextRunAt` / `nextSettleAt` 并重新放入两级直址表。

`nextRunAt` 必须存档。加载时恢复已有 Task，不能再创建一条。同时只保留一条未来的当日检测。常规评估不单独再排周期任务；紧急评估使用 `NPC_REEVALUATE`，每个势力最多一条。非今日任务放在 `_tasks`，到日切时才晋升到 `_todayTasks`。

## 6. 查询索引与状态变更

``` ts
interface WorldIndexes {
  partyIdsByFaction: Map<EntityId, Set<EntityId>>;
  settlementIdsByFaction: Map<EntityId, Set<EntityId>>;
  movingPartyIds: Set<EntityId>;
  partyIdsByLocation: Map<MapNodeId, Set<EntityId>>;
  activeBattleIds: Set<EntityId>;
}
```

索引加速"按势力、位置、状态"查询，避免每次扫描全部实体。索引属于派生数据，可以从权威状态重建。

``` ts
interface WorldMutationService {
  transferParty(partyId: EntityId, newFactionId: EntityId): void;
  movePartyToLocation(partyId: EntityId, locationId: MapNodeId): void;
  destroyParty(partyId: EntityId): void;
  transferSettlement(settlementId: EntityId, newFactionId: EntityId): void;
}
```

所有影响索引的状态变更都应通过统一入口，同时更新实体和索引。`Party.factionId`
是归属的权威事实，索引不能反过来成为另一份权威数据。

## 7. 地图与寻路

``` ts
type TerrainType =
  | "plain" | "forest" | "hill" | "mountain" | "swamp";

interface MapNode {
  id: MapNodeId;
  kind: "town" | "castle" | "village" | "road" | "wilderness";
  x: number;
  y: number;
  terrain: TerrainType;
  settlementId?: EntityId;
}

interface MapEdge {
  id: string;
  from: MapNodeId;
  to: MapNodeId;
  distance: number;
  terrain: TerrainType;
  movementCost: number;
  bidirectional: boolean;
}

interface WorldMap {
  nodes: Map<MapNodeId, MapNode>;
  edges: Map<string, MapEdge>;
  outgoingEdges: Map<MapNodeId, MapEdge[]>;
}

interface PathfindingRequest {
  startNodeId: MapNodeId;
  goalNodeId: MapNodeId;
  partyId: EntityId;
  allowHostileTerritory: boolean;
}

interface PathResult {
  route: MapNodeId[];
  totalCost: number;
  mapVersion: number;
}

interface PathfindingService {
  findPath(request: PathfindingRequest): PathResult | null;
}
```

`outgoingEdges` 是邻接表，只遍历当前节点的相邻道路。推荐 A\*
做常规寻路，Dijkstra
可用于校验。成本可考虑距离、地形、道路、敌方威胁和通行条件。`mapVersion`
用于判断路径缓存是否需要重新验证。

## 8. NPC AI 接口

### 8.1 观察信息

``` ts
interface PartyObservation {
  partyId: EntityId;
  factionId: EntityId;
  locationId: MapNodeId;
  estimatedSoldiers: number;
  estimatedStrength: number;
  confidence: number;
}

interface StrategicObservation {
  actorFactionId: EntityId;
  now: GameTime;
  ownPartyIds: EntityId[];
  knownEnemyParties: PartyObservation[];
  knownSettlementIds: EntityId[];
  knownWars: EntityId[];
  availableFood: number;
  availableGold: number;
}
```

AI 只应看到符合其情报权限的 `Observation`，而不是直接读取完整
`WorldState`。这能防止全图透视，也便于测试情报不完整时的决策。

### 8.2 候选动作与结果

``` ts
type StrategicAction =
  | { type: "MOVE"; partyId: EntityId; destinationNodeId: MapNodeId }
  | { type: "ATTACK"; partyId: EntityId; targetPartyId: EntityId }
  | { type: "BESIEGE"; partyId: EntityId; settlementId: EntityId }
  | { type: "RESUPPLY"; partyId: EntityId; settlementId: EntityId }
  | { type: "RETREAT"; partyId: EntityId; destinationNodeId: MapNodeId };

interface DecisionResult<TAction> {
  action: TAction;
  score: number;
  reasonCode: string;
  scoreBreakdown: Record<string, number>;
}

interface StrategicAI {
  decide(observation: StrategicObservation):
    DecisionResult<StrategicAction> | null;
}

interface ActionExecutor {
  validate(action: StrategicAction): ValidationResult;
  execute(action: StrategicAction): ActionExecutionResult;
}
```

判别联合类型约束各动作的必需参数。评分明细用于解释 AI
为什么选择某行动。AI 只提出行动，最终由执行器校验并修改世界状态。

## 9. 战斗数据

``` ts
interface BattleUnit {
  id: EntityId;
  sourcePartyId: EntityId;
  troopTypeId: string;
  count: number;
  position: { x: number; y: number };
  morale: number;
  fatigue: number;
  formationIntegrity: number;
  ammunition: number;
  status: "active" | "retreating" | "routed" | "destroyed";
  currentOrder: BattleOrder;
}

type BattlePhase =
  | "deployment"
  | "command"
  | "movement"
  | "ranged_combat"
  | "melee_combat"
  | "morale"
  | "resolution"
  | "finished";

interface Battle {
  id: EntityId;
  attackerPartyId: EntityId;
  defenderPartyId: EntityId;
  phase: BattlePhase;
  phaseStartedAt: GameTime;
  phaseEndsAt?: GameTime;
```

战略军队与战场小队是不同层级。战斗时展开为
`BattleUnit`，战后把伤亡、俘虏、士气和补给变化同步回战略军队。阶段事件需携带版本号，防止结束后的旧事件重复结算。

``` ts
type TroopTag =
```

## 10. 经济与资源账本

``` ts
interface EconomyAccount {
  ownerId: EntityId;
  balances: Map<ResourceId, number>;
}

interface ResourceChange {
  resourceId: ResourceId;
  delta: number;
  reasonCode: string;
  sourceEntityId?: EntityId;
}

interface EconomyService {
  canAfford(ownerId: EntityId, costs: ResourceChange[]): boolean;
  applyChanges(ownerId: EntityId, changes: ResourceChange[]): void;
}

interface EconomyLedgerEntry {
  id: string;
  ownerId: EntityId;
  resourceId: ResourceId;
  delta: number;
  reasonCode: string;
  relatedEntityId?: EntityId;
  occurredAt: GameTime;
  sourceEventId?: EventId;
}
```

当前余额用于快速查询；账本用于追踪变化来源和排查重复结算。多资源扣除必须先统一校验，再原子提交，避免只扣了一部分资源。

行军粮食以 `Party.food` 的锚点为准，不在账本或当日检测里再扣一次。城镇库存和势力金库是各自的余额。账本只追加变化，不充当第二份余额。

## 11. 历史日志与随机数

``` ts
interface WorldLogEntry {
  id: string;
  occurredAt: GameTime;
  category: "military" | "economy" | "diplomacy" | "ai" | "system";
  eventType: string;
  entityIds: EntityId[];
  reasonCode: string;
  details: Record<string, unknown>;
}

interface RngSnapshot {
  words: number[];
}

interface RandomSource {
  nextFloat(): number;
  nextInt(minInclusive: number, maxInclusive: number): number;
  getState(): RngSnapshot;
  setState(state: RngSnapshot): void;
}

interface RandomStreams {
  combat: RandomSource;
  economy: RandomSource;
  events: RandomSource;
  world: RandomSource;
}
```

随机数状态应完整保存。`RngSnapshot.words` 容纳实际 PRNG 的全部状态字，不要压成一个数字。不同系统使用独立随机流，可以减少一个系统多调用一次随机数对其他系统结果的影响。确定性回放还要求稳定的遍历顺序、事件排序和规则版本。实体 ID 来自存档里的 `nextEntitySequence`，不能用随机 UUID。

历史日志记录已经发生的变化，TaskRepository 与两级调度表记录未来要做的工作，两者职责不同。

## 12. 活动、命令与阻塞决定

``` ts
type ActivityStatus =
  | "scheduled"
  | "active"
  | "paused"
  | "completed"
  | "failed"
  | "cancelled";

interface Activity {
  id: EntityId;
  type: "march" | "siege" | "training" | "hero-visit";
  status: ActivityStatus;
  revision: number;
  startTime: GameTime | null;
  expectedEndTime: GameTime | null;
  participantIds: EntityId[];
  march?: MarchActivityData;
}

interface PendingDecision {
  id: EntityId;
  eventId: EventId;
  promptCode: string;
  openedAt: GameTime;
}

interface CommandLogEntry {
  id: string;
  acceptedAt: GameTime;
  command: PlayerCommand;
}
```

活动是持续任务的唯一生命周期。`expectedEndTime` 只是预计结束时间，改道或提前离开后，原事件会因版本不符被跳过。`revision` 从 1 开始，每次取消、完成或改变计划都加一。

`PendingDecision` 非空时，游戏时间停在 `openedAt`（PauseWorld）。播放器不能继续 `advance` 越过该点，直到玩家命令清空它；其他 ContinueWorld 的 Waiting 不隐含此语义。

`CommandLogEntry` 按游戏分钟记录已接受的命令，供回放。它不是世界历史日志，也不记录真实时间的帧间隔。

玩家菜单和自由文字应统一转换为结构化 `PlayerCommand`，等当前区间结算返回后再执行。

## 13. 存档 DTO

运行时可以用 `Map`、`Set` 和 `DirectAddressTable`；存档使用版本化 DTO：

``` ts
    savedAt: string;
    gameVersion: string;
    rulesVersion: string;
  };
}
```

这是示意结构。播放器速率是客户端偏好，不放进世界快照。

建议保存：权威状态、锚点余数、整数世界时间及换算余数、随机流、所有单调序号、TaskRecord、ExecutionRecord、DurableResultInbox、资源/依赖等待、幂等账本、活动、PauseWorld/因果屏障和规则版本。

通常可重建：查询索引、路径缓存、不会影响未来行为的临时缓存。若 AI
目标锁定或长期记忆会影响后续行为，则必须保存或无损重建。数组写入前按 ID 排序。

WorldState、WorldClock、TaskRecord、ExecutionRecord、ResultInbox 与幂等账本必须来自同一原子快照或日志事务。

加载流程：验证版本 -\> 迁移旧格式 -\> 恢复实体、TaskRecord、ExecutionRecord 和幂等账本 -\> 按 `nextSettleAt` 重建未来表/今日表/overflow -\>
重建 Ready、resource/dependency waiters -\> 按 RecoveryPolicy 恢复外部异步 -\> 校验引用 -\> 恢复模拟。

## 14. 服务边界

``` ts
interface WorldRuntime {
  readonly query: WorldQueryService;
  readonly rules: WorldRuleService;
  readonly actions: WorldActionService;
  readonly scheduleIndex: TaskScheduleIndex;
  readonly readyScheduler: TaskReadyScheduler;
  readonly resources: TaskResourceArbiter;
  readonly dependencies: TaskDependencyGraph;
  readonly executions: TaskExecutionRepository;
  readonly resultInbox: DurableResultInbox;
  readonly taskPipeline: TaskPipeline;
  readonly commits: SerialCommitQueue;
  readonly driver: WorldDriver;
  readonly session: SessionPlayer;
}
```

-   **Query**：只读查询，避免副作用。
-   **Rules / Validator**：检查移动、招募、攻城等前置条件。
-   **Actions / Executor**：统一修改状态、同步索引、扣资源、记日志和注册 Task 边界。不能嵌套区间结算或私自拨时钟。
-   **ScheduleIndex**：维护两级直址表和 overflow，只决定“何时到期”。
-   **ReadyScheduler**：按 deadline/priority/sequence 选择，并旁路资源受阻队头。
-   **Resource / Dependency**：显式互斥、依赖等待、唤醒和死锁/环检测。
-   **ResultInbox**：持久化外部结果，在内核安全点按 commandSequence 去重消费。
-   **TaskPipeline / Gates**：触发、开始、提交三个安全点复验；CommitGate 校验 readSet/entityVersion。
-   **Driver**：在线 Tick 与 advance 的唯一绝对边界推进器。
-   **Session**：按速率驱动 Tick 或 `advance`。PauseWorld 未决时 advance 不继续。

`readonly`
不会自动阻止引用对象内部修改；需要通过模块边界、只读查询模型和统一写入服务保证状态保护。

## 15. 数据结构选型总结

  需求              推荐结构            作用
  ----------------- ------------------- ----------------------
  按 ID 查实体      `Map`               快速定位
  按势力/地点查询   `Map + Set` 索引    减少全量遍历
  未来 Task         滚动日直址表+overflow 日切晋升且支持窗口外
  今日 Task         按日内分钟直址表    只提取命中的分钟槽
  cadence           `TaskSettleLevel`   计算 nextSettleAt
  执行顺序          ReadyScheduler      deadline/priority/sequence
  互斥/依赖         ResourceArbiter+Graph 显式资源、serialKey、dependsOn
  Task 有效性       三段 Gate           deadline/revision/version/幂等
  单次执行          ExecutionRecord     支持多实例、恢复和审计
  异步结果          DurableResultInbox  安全点消费、去重、崩溃恢复
  Task 取消         revision + 惰性跳过 无需搜索所有槽
  道路关系          邻接表              高效遍历相邻节点
  寻路              A\*                 减少搜索范围
  NPC 行动          判别联合类型        参数明确、类型安全
  战斗阶段          状态机 + 联合类型   限制非法状态转移
  兵种能力          配置表 + 标签       数据驱动、减少硬编码
  经济              余额 + 追加式账本   快速查询与审计
  历史              追加式日志          复盘和调试
  随机模拟          可保存状态的 PRNG   确定性回放
  存档              版本化 DTO          可迁移、可恢复

## 16. 推荐开发顺序

1.  `WorldState`、实体 ID 和核心实体。
2.  整数 WorldClock、WorldDriver 绝对边界推进、两级 ScheduleIndex。
3.  TaskExecutionRequest、ExecutionRecord、ReadyScheduler、ResourceArbiter、三段 Gate 与版本化提交。
4.  地图邻接表与 A\*。
5.  行军状态、行动对象和抵达 Task。
6.  战斗小队与阶段状态机。
7.  AI Observation、候选动作和执行器。
8.  经济账户与账本。
9.  随机数、历史日志、存档 DTO。
10. 确定性回放、批量战斗和长期模拟测试。

**核心判断：分级事件只能做派生通知；先建立统一边界推进、显式资源/依赖、ExecutionRecord 和版本化提交，再扩展业务 Task。**
