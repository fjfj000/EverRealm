# 数据结构

## 1. 设计原则

数据结构需要服务于世界模拟、事件调度、纯程序 AI、存档和调试。核心原则：

1.  权威状态与查询索引分离。
2.  实体之间通过 ID 关联，避免深层嵌套。
3.  AI 决策与状态修改分离。
4.  当前状态、未来事件、历史记录分离。
5.  运行时结构与存档 DTO 分离。
6.  先选择简单可靠的结构，再通过性能测试优化。

## 2. 核心类型与 WorldState

``` ts
type EntityId = string;
type GameTime = number; // 整数分钟
type EventId = string;
type ResourceId = string;
type MapNodeId = EntityId;

interface WorldState {
  schemaVersion: number;
  currentTime: GameTime;
  taskIntervalMinutes: number;
  nextEntitySequence: number;
  nextEventSequence: number;
  rngStates: Record<string, RngSnapshot>;
  playerId: EntityId;
  pendingDecision: PendingDecision | null;

  characters: Map<EntityId, Character>;
  parties: Map<EntityId, Party>;
  settlements: Map<EntityId, Settlement>;
  factions: Map<EntityId, Faction>;
  battles: Map<EntityId, Battle>;
  wars: Map<EntityId, War>;
  activities: Map<EntityId, Activity>;
}
```

### 为什么用 `Map<EntityId, Entity>`？

-   按 ID 查询的平均时间复杂度通常为 `O(1)`。
-   实体之间通过 ID 关联，降低深层嵌套和循环引用。
-   迁移实体归属更容易。
-   查询索引可以从权威实体重建。

`Map` 不适合所有条件查询。按 ID 查实体用
`Map`；按势力、位置或状态查找则建立专门索引。存档时需将 `Map`
转为可序列化 DTO，不能直接依赖 `JSON.stringify()` 序列化其条目。

待处理事件不属于 `WorldState`。它们由事件队列保存，存档时单独写入调度器快照。`pendingDecision` 表示时间引擎停在一个阻塞事件上，播放器在它被清空之前不能继续推进。

`taskIntervalMinutes` 是一天的长度，默认 1440，可以配置，并且要写入存档。`advanceTo` 用它划分检测区间，一次只激活当前区间里的任务。

## 3. 核心实体

### 3.1 人物

``` ts
interface Character {
  id: EntityId;
  name: string;
  factionId?: EntityId;
  partyId?: EntityId;
  skills: Record<string, number>;
  health: number;
  morale: number;
  relationshipIds: EntityId[];
  traits: string[];
}
```

普通士兵通常不必逐个建 `Character`。将领、重要 NPC
或具有独立关系与剧情的人物才需要独立实体。

### 3.2 战略军队与兵力编组

``` ts
interface Party {
  id: EntityId;
  factionId: EntityId;
  locationId: MapNodeId;
  troopStacks: TroopStack[];
  food: AnchoredQuantity;
  gold: number;
  morale: number;
  activityId?: EntityId;
  activeBattleId?: EntityId;
}

interface TroopStack {
  troopTypeId: string;
  count: number;
  experience: number;
  equipmentTier: number;
}

interface AnchoredQuantity {
  value: number;
  remainder: number;
  anchoredAt: GameTime;
  rateNumerator: number;
  rateDenominator: number;
}

interface MarchActivityData {
  route: MapNodeId[];
  segmentIndex: number;
  speedPerMinute: number;
}
```

`TroopStack` 表示战略层兵力聚合；`BattleUnit`
表示战场小队。不要把两种状态混成同一个接口。

`locationId` 是队伍当前所在节点。行军路线放在行军活动的 `MarchActivityData` 里，不在队伍上再存一份移动计划。`food` 用锚点保存，日结算不从这里重复扣除。

### 3.3 城镇与势力

``` ts
interface Settlement {
  id: EntityId;
  name: string;
  factionId: EntityId;
  population: number;
  gold: number;
  food: number;
  materials: Record<string, number>;
  prosperity: number;
  security: number;
  garrisonPartyIds: EntityId[];
}

interface Faction {
  id: EntityId;
  name: string;
  rulerId: EntityId;
  treasury: number;
  policies: string[];
  strategicGoal?: StrategicGoal;
}
```

实体保存当前状态；税收公式、生产规则、战略逻辑放在系统中。队伍和城镇上的 `factionId` 是归属的权威事实。按势力枚举队伍或城镇时走索引，不在势力上再存一份 ID 列表。城镇的 `food` 是库存，由当日检测增减；它和队伍行军口粮不是同一份数量。

## 4. 事件结构与调度器

### 4.1 判别联合类型

``` ts
interface EventBase {
  id: EventId;
  dueTime: GameTime;
  priority: number;
  sequence: number;
  blocking: boolean;
  activityId?: EntityId;
  activityRevision?: number;
}

type WorldEvent =
  | (EventBase & { type: "DAY_TICK" })
  | (EventBase & {
      type: "PARTY_ARRIVED";
      payload: { partyId: EntityId; nodeId: MapNodeId };
    })
  | (EventBase & {
      type: "ACTIVITY_DEADLINE";
      payload: { activityId: EntityId };
    })
  | (EventBase & {
      type: "FOOD_EXHAUSTED";
      payload: { partyId: EntityId };
    })
  | (EventBase & {
      type: "BATTLE_PHASE_END";
      payload: { battleId: EntityId; phaseVersion: number };
    })
  | (EventBase & {
      type: "NPC_REEVALUATE";
      payload: { factionId: EntityId };
    });
```

优点：事件类型决定 payload
形状，编译器可检查字段，新增事件可做穷尽检查，减少运行时错误。

`blocking` 是这件事件要不要时停。英雄拜访的离开事件为 `false`。必须等玩家选择的决定为 `true`。优先级数字小的先执行：阈值 100，阻塞决定 110，活动节点 120，战斗阶段 130，紧急评估 140，当日检测 200。

事件还要先看属于哪一天。`floor(dueTime / taskIntervalMinutes)` 与当前区间不同的事件，这次 `advanceTo` 不激活。更早的天出队并跳过；更晚的天留在队列里。

### 4.2 事件状态

``` ts
type EventStatus =
  | "pending"
  | "processing"
  | "completed"
  | "cancelled"
  | "stale";
```

不要把"已出队"和"已取消"共用一个状态。

### 4.3 调度器接口

``` ts
interface EventScheduler {
  schedule(event: WorldEvent): void;
  peekNext(): WorldEvent | undefined;
  popNext(): WorldEvent | undefined;
  cancel(eventId: EventId): boolean;
  hasPendingEvents(): boolean;
}
```

推荐二叉最小堆：查看队首 `O(1)`，插入和出队 `O(log n)`。比较键是
`dueTime` 升序、`priority` 升序、`sequence` 升序。不要复用只比较数字的
`assets/src/framwork/data_structures/min_heap.ts`。

取消事件可使用活动版本号加懒删除。改道或取消时活动版本加一；旧事件到期时版本不符，标记为过期并忽略。早于当前检测区间，或今天里已经早于 `currentTime` 的事件，出队并跳过，不改状态，也不中断推进。监控过期事件比例，必要时重建堆。

已完成事件不留在堆里，也不写入存档。存档只保存仍待执行的事件。

## 5. 周期任务

``` ts
interface DayTickSchedule {
  nextRunAt: GameTime;
}
```

当日检测的间隔就是 `WorldState.taskIntervalMinutes`，优先级 200。它处理生产、税收、军饷、英雄刷新、无法预测的相遇和常规战略评估。执行后把下一次排在再往后一个区间的起点。

`nextRunAt` 必须存档。加载时恢复已有的 `DAY_TICK`，不能再创建一条。同时只保留一条未来的当日检测。常规评估不单独再排周期任务；紧急评估使用 `NPC_REEVALUATE`，每个势力最多一条。不属于今天的紧急评估也留在队列里，等那一天再激活。

## 6. 查询索引与状态变更

``` ts
interface WorldIndexes {
  partyIdsByFaction: Map<EntityId, Set<EntityId>>;
  settlementIdsByFaction: Map<EntityId, Set<EntityId>>;
  movingPartyIds: Set<EntityId>;
  partyIdsByLocation: Map<MapNodeId, Set<EntityId>>;
  activeBattleIds: Set<EntityId>;
}
```

索引加速"按势力、位置、状态"查询，避免每次扫描全部实体。索引属于派生数据，可以从权威状态重建。

``` ts
interface WorldMutationService {
  transferParty(partyId: EntityId, newFactionId: EntityId): void;
  movePartyToLocation(partyId: EntityId, locationId: MapNodeId): void;
  destroyParty(partyId: EntityId): void;
  transferSettlement(settlementId: EntityId, newFactionId: EntityId): void;
}
```

所有影响索引的状态变更都应通过统一入口，同时更新实体和索引。`Party.factionId`
是归属的权威事实，索引不能反过来成为另一份权威数据。

## 7. 地图与寻路

``` ts
type TerrainType =
  | "plain" | "forest" | "hill" | "mountain" | "swamp";

interface MapNode {
  id: MapNodeId;
  kind: "town" | "castle" | "village" | "road" | "wilderness";
  x: number;
  y: number;
  terrain: TerrainType;
  settlementId?: EntityId;
}

interface MapEdge {
  id: string;
  from: MapNodeId;
  to: MapNodeId;
  distance: number;
  terrain: TerrainType;
  movementCost: number;
  bidirectional: boolean;
}

interface WorldMap {
  nodes: Map<MapNodeId, MapNode>;
  edges: Map<string, MapEdge>;
  outgoingEdges: Map<MapNodeId, MapEdge[]>;
}

interface PathfindingRequest {
  startNodeId: MapNodeId;
  goalNodeId: MapNodeId;
  partyId: EntityId;
  allowHostileTerritory: boolean;
}

interface PathResult {
  route: MapNodeId[];
  totalCost: number;
  mapVersion: number;
}

interface PathfindingService {
  findPath(request: PathfindingRequest): PathResult | null;
}
```

`outgoingEdges` 是邻接表，只遍历当前节点的相邻道路。推荐 A\*
做常规寻路，Dijkstra
可用于校验。成本可考虑距离、地形、道路、敌方威胁和通行条件。`mapVersion`
用于判断路径缓存是否需要重新验证。

## 8. NPC AI 接口

### 8.1 观察信息

``` ts
interface PartyObservation {
  partyId: EntityId;
  factionId: EntityId;
  locationId: MapNodeId;
  estimatedSoldiers: number;
  estimatedStrength: number;
  confidence: number;
}

interface StrategicObservation {
  actorFactionId: EntityId;
  now: GameTime;
  ownPartyIds: EntityId[];
  knownEnemyParties: PartyObservation[];
  knownSettlementIds: EntityId[];
  knownWars: EntityId[];
  availableFood: number;
  availableGold: number;
}
```

AI 只应看到符合其情报权限的 `Observation`，而不是直接读取完整
`WorldState`。这能防止全图透视，也便于测试情报不完整时的决策。

### 8.2 候选动作与结果

``` ts
type StrategicAction =
  | { type: "MOVE"; partyId: EntityId; destinationNodeId: MapNodeId }
  | { type: "ATTACK"; partyId: EntityId; targetPartyId: EntityId }
  | { type: "BESIEGE"; partyId: EntityId; settlementId: EntityId }
  | { type: "RESUPPLY"; partyId: EntityId; settlementId: EntityId }
  | { type: "RETREAT"; partyId: EntityId; destinationNodeId: MapNodeId };

interface DecisionResult<TAction> {
  action: TAction;
  score: number;
  reasonCode: string;
  scoreBreakdown: Record<string, number>;
}

interface StrategicAI {
  decide(observation: StrategicObservation):
    DecisionResult<StrategicAction> | null;
}

interface ActionExecutor {
  validate(action: StrategicAction): ValidationResult;
  execute(action: StrategicAction): ActionExecutionResult;
}
```

判别联合类型约束各动作的必需参数。评分明细用于解释 AI
为什么选择某行动。AI 只提出行动，最终由执行器校验并修改世界状态。

## 9. 战斗数据

``` ts
interface BattleUnit {
  id: EntityId;
  sourcePartyId: EntityId;
  troopTypeId: string;
  count: number;
  position: { x: number; y: number };
  morale: number;
  fatigue: number;
  formationIntegrity: number;
  ammunition: number;
  status: "active" | "retreating" | "routed" | "destroyed";
  currentOrder: BattleOrder;
}

type BattlePhase =
  | "deployment"
  | "command"
  | "movement"
  | "ranged_combat"
  | "melee_combat"
  | "morale"
  | "resolution"
  | "finished";

interface Battle {
  id: EntityId;
  attackerPartyId: EntityId;
  defenderPartyId: EntityId;
  phase: BattlePhase;
  phaseStartedAt: GameTime;
  phaseEndsAt?: GameTime;
  unitIds: EntityId[];
  round: number;
  status: "active" | "finished";
}
```

战略军队与战场小队是不同层级。战斗时展开为
`BattleUnit`，战后把伤亡、俘虏、士气和补给变化同步回战略军队。阶段事件需携带版本号，防止结束后的旧事件重复结算。

### 兵种配置与标签

``` ts
type TroopTag =
  | "light-infantry" | "heavy-infantry" | "spear"
  | "light-cavalry" | "heavy-cavalry" | "ranged"
  | "shielded" | "anti-cavalry";

interface TroopDefinition {
  id: string;
  name: string;
  tags: Set<TroopTag>;
  attack: number;
  defense: number;
  armor: number;
  speed: number;
  rangedAttack?: number;
  range?: number;
  upkeepPerDay: number;
}
```

兵种定义是只读配置，小队只保存兵种 ID
和动态状态。标签用于通用克制规则；特殊能力可以另建能力配置，不要把所有差异都硬塞进标签。

## 10. 经济与资源账本

``` ts
interface EconomyAccount {
  ownerId: EntityId;
  balances: Map<ResourceId, number>;
}

interface ResourceChange {
  resourceId: ResourceId;
  delta: number;
  reasonCode: string;
  sourceEntityId?: EntityId;
}

interface EconomyService {
  canAfford(ownerId: EntityId, costs: ResourceChange[]): boolean;
  applyChanges(ownerId: EntityId, changes: ResourceChange[]): void;
}

interface EconomyLedgerEntry {
  id: string;
  ownerId: EntityId;
  resourceId: ResourceId;
  delta: number;
  reasonCode: string;
  relatedEntityId?: EntityId;
  occurredAt: GameTime;
  sourceEventId?: EventId;
}
```

当前余额用于快速查询；账本用于追踪变化来源和排查重复结算。多资源扣除必须先统一校验，再原子提交，避免只扣了一部分资源。

行军粮食以 `Party.food` 的锚点为准，不在账本或当日检测里再扣一次。城镇库存和势力金库是各自的余额。账本只追加变化，不充当第二份余额。

## 11. 历史日志与随机数

``` ts
interface WorldLogEntry {
  id: string;
  occurredAt: GameTime;
  category: "military" | "economy" | "diplomacy" | "ai" | "system";
  eventType: string;
  entityIds: EntityId[];
  reasonCode: string;
  details: Record<string, unknown>;
}

interface RngSnapshot {
  words: number[];
}

interface RandomSource {
  nextFloat(): number;
  nextInt(minInclusive: number, maxInclusive: number): number;
  getState(): RngSnapshot;
  setState(state: RngSnapshot): void;
}

interface RandomStreams {
  combat: RandomSource;
  economy: RandomSource;
  events: RandomSource;
  world: RandomSource;
}
```

随机数状态应完整保存。`RngSnapshot.words` 容纳实际 PRNG 的全部状态字，不要压成一个数字。不同系统使用独立随机流，可以减少一个系统多调用一次随机数对其他系统结果的影响。确定性回放还要求稳定的遍历顺序、事件排序和规则版本。实体 ID 来自存档里的 `nextEntitySequence`，不能用随机 UUID。

历史日志记录已经发生的变化，事件队列记录未来要做的工作，两者职责不同。

## 12. 活动、命令与阻塞决定

``` ts
type ActivityStatus =
  | "scheduled"
  | "active"
  | "paused"
  | "completed"
  | "failed"
  | "cancelled";

interface Activity {
  id: EntityId;
  type: "march" | "siege" | "training" | "hero-visit";
  status: ActivityStatus;
  revision: number;
  startTime: GameTime | null;
  expectedEndTime: GameTime | null;
  participantIds: EntityId[];
  march?: MarchActivityData;
}

interface PendingDecision {
  id: EntityId;
  eventId: EventId;
  promptCode: string;
  openedAt: GameTime;
}

interface CommandLogEntry {
  id: string;
  acceptedAt: GameTime;
  command: PlayerCommand;
}
```

活动是持续任务的唯一生命周期。`expectedEndTime` 只是预计结束时间，改道或提前离开后，原事件会因版本不符被跳过。`revision` 从 1 开始，每次取消、完成或改变计划都加一。

`PendingDecision` 非空时，游戏时间停在 `openedAt`。播放器不能继续 `advanceTo`，直到玩家命令清空它。

`CommandLogEntry` 按游戏分钟记录已接受的命令，供回放。它不是世界历史日志，也不记录真实时间的帧间隔。

玩家菜单和自由文字应统一转换为结构化 `PlayerCommand`，等当前 `advanceTo` 返回后再执行。

## 13. 存档 DTO

运行时可以用 `Map`、`Set` 和最小堆；存档使用版本化 DTO：

``` ts
interface GameSaveV1 {
  schemaVersion: 1;
  world: {
    currentTime: GameTime;
    taskIntervalMinutes: number;
    nextEntitySequence: number;
    rngStates: Record<string, RngSnapshot>;
    playerId: EntityId;
    pendingDecision: PendingDecision | null;
    characters: Character[];
    parties: Party[];
    settlements: Settlement[];
    factions: Faction[];
    battles: Battle[];
    wars: War[];
    activities: Activity[];
  };
  scheduler: {
    nextEventSequence: number;
    pendingEvents: WorldEvent[];
    dayTick: DayTickSchedule;
  };
  metadata: {
    savedAt: string;
    gameVersion: string;
    rulesVersion: string;
  };
}
```

这是示意结构。播放器速率是客户端偏好，不放进世界快照。

建议保存：权威状态、锚点余数、世界时间、检测间隔、随机流、两类序号、待执行事件、下一次当日检测、活动、阻塞决定、规则版本。

通常可重建：查询索引、路径缓存、不会影响未来行为的临时缓存。若 AI
目标锁定或长期记忆会影响后续行为，则必须保存或无损重建。数组写入前按 ID 排序。

加载流程：验证版本 -\> 迁移旧格式 -\> 恢复实体 -\> 重建索引与事件堆 -\>
校验引用与事件 -\> 恢复模拟。

## 14. 服务边界

``` ts
interface WorldRuntime {
  readonly query: WorldQueryService;
  readonly rules: WorldRuleService;
  readonly actions: WorldActionService;
  readonly scheduler: EventScheduler;
  readonly driver: WorldDriver;
  readonly session: SessionPlayer;
}
```

-   **Query**：只读查询，避免副作用。
-   **Rules / Validator**：检查移动、招募、攻城等前置条件。
-   **Actions / Executor**：统一修改状态、同步索引、扣资源、记日志和安排事件。不能调用 `advanceTo`。
-   **Scheduler**：只负责入队、出队和排序，不拨动时钟。
-   **Driver**：`advanceTo`。唯一允许向前拨动世界时钟的模块。
-   **Session**：按速率把真实时间换成游戏分钟，再调用驱动器。阻塞决定未完成时不调用。

`readonly`
不会自动阻止引用对象内部修改；需要通过模块边界、只读查询模型和统一写入服务保证状态保护。

## 15. 数据结构选型总结

  需求              推荐结构            作用
  ----------------- ------------------- ----------------------
  按 ID 查实体      `Map`               快速定位
  按势力/地点查询   `Map + Set` 索引    减少全量遍历
  最早到期事件      三键最小堆          时间、优先级、序号
  未知事件          可配置的一天        一次只检测当前区间
  已知分钟          精确事件            只在所属的那一天激活
  事件取消          活动版本 + 懒删除   避免搜索堆中间元素
  道路关系          邻接表              高效遍历相邻节点
  寻路              A\*                 减少搜索范围
  NPC 行动          判别联合类型        参数明确、类型安全
  战斗阶段          状态机 + 联合类型   限制非法状态转移
  兵种能力          配置表 + 标签       数据驱动、减少硬编码
  经济              余额 + 追加式账本   快速查询与审计
  历史              追加式日志          复盘和调试
  随机模拟          可保存状态的 PRNG   确定性回放
  存档              版本化 DTO          可迁移、可恢复

## 16. 推荐开发顺序

1.  `WorldState`、实体 ID 和核心实体。
2.  事件联合类型与最小堆。
3.  查询索引与统一状态变更服务。
4.  地图邻接表与 A\*。
5.  行军状态、行动对象和抵达事件。
6.  战斗小队与阶段状态机。
7.  AI Observation、候选动作和执行器。
8.  经济账户与账本。
9.  随机数、历史日志、存档 DTO。
10. 确定性回放、批量战斗和长期模拟测试。

**核心判断：先把权威状态、事件队列、状态变更入口和可复现测试做好，再逐步优化性能。对
MVP 来说，清晰的接口边界比过早引入复杂基础设施更重要。**
